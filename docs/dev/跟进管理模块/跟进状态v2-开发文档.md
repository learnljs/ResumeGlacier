# 跟进状态 v2 开发文档

> 基于 PRD：`doc/product/简历状态v2.md`
> 编写日期：2026-07-29

---

## 一、需求概述

将跟进状态从现有的 **6 个**（沟通中 / 待面试 / 已面试 / 已录用 / 已离职 / 不合适）扩展为 **10 个**：

| # | 状态名 | 枚举值 | 说明 |
|---|--------|--------|------|
| 1 | 沟通中 | `CONTACTING` | 初次接触，正在跟进 |
| 2 | 待面试 | `INTERVIEW_SCHEDULED` | 等待安排面试 |
| 3 | 已面试 | `INTERVIEWED` | 面试完成，等待结果 |
| 4 | 已发offer | `OFFER_SENT` | **新增** — 已发出 offer |
| 5 | 待入职 | `PENDING_ONBOARD` | **新增** — 候选人已确认，等待入职 |
| 6 | 已入职 | `HIRED` | 原"已录用"，值不变 |
| 7 | 已离职 | `RESIGNED` | 入职后又离职 |
| 8 | 拒offer | `OFFER_REJECTED` | **新增** — 候选人拒绝 offer |
| 9 | 取消面试 | `INTERVIEW_CANCELLED` | **新增** — 面试取消 |
| 10 | 不合适 | `UNSUITABLE` | 筛选/跟进后判定不合适 |

### 核心变更点

1. **"已录用"拆分为三段**：已发offer → 待入职 → 已入职
2. **拒绝场景细分**：不合适 / 拒offer / 取消面试，共用 `rejectReason` 字段
3. **统一回退机制**：任意状态可回退到上游状态，需填写回退原因
4. **关键节点强制字段**：切换状态前必须填写对应信息
5. **列表内联编辑权限控制**：不同时间字段仅在特定 Tab 可修改
6. **操作日志增强**：所有状态变更（含回退）全量记入 `FollowUpLog`

## 二、技术架构

### 整体结构

```
┌─────────────────────────────────────────────────┐
│  前端 (app/resume/follow-up/page.tsx)              │
│  ├─ 10 Tab 布局                                   │
│  ├─ FOLLOW_UP_ACTIONS 配置对象 (按钮/弹窗/字段映射) │
│  ├─ 现有弹窗组件复用                               │
│  └─ 内联编辑 (interviewTime/startDate/resignedAt)  │
├─────────────────────────────────────────────────┤
│  API (app/api/follow-up/records/)                  │
│  ├─ PATCH /[id]  — 状态切换 + 内联编辑             │
│  └─ GET /       — 列表查询 (已有 recordStatus 参数) │
├─────────────────────────────────────────────────┤
│  状态机 (lib/services/follow-up-transitions.ts)    │
│  ├─ TRANSITIONS 流转配置                           │
│  └─ validateTransition() 校验函数                   │
├─────────────────────────────────────────────────┤
│  数据层 (prisma/schema.prisma)                     │
│  ├─ FollowUpRecord.status 枚举值扩展               │
│  └─ 无新增字段                                     │
└─────────────────────────────────────────────────┘
```

### 设计原则

- **状态机唯一真相源**：流转规则在后端 `validateTransition()` 集中定义，前端 `FOLLOW_UP_ACTIONS` 镜像之
- **弹窗复用**：`UnsuitableDialog` 通过 `title` prop 覆盖不合适/取消面试/拒offer 三种场景
- **无新增字段**：现有 `FollowUpRecord` 字段已全部覆盖 PRD 需求
- **最小改动**：在现有 PATCH 模式上扩展，不新增 API 路由

## 三、数据模型

### 3.1 FollowUpRecord 字段说明

| 字段 | 类型 | 用途 | 关联状态 |
|------|------|------|---------|
| `status` | String | 状态枚举 (10 个值) | 全部 |
| `interviewTime` | String? | 面试时间 | 待面试 |
| `startDate` | String? | 入职时间 (预计/实际共用) | 已发offer、待入职、已入职 |
| `rejectReason` | String? | 拒绝/取消/拒offer 原因 (共用) | 不合适、取消面试、拒offer |
| `resignedAt` | DateTime? | 离职日期 | 已离职 |
| `resignReason` | String? | 离职原因 | 已离职 |
| `salaryRange` | String? | 薪资范围 | 已发offer |
| `jobLevel` | String? | 岗位级别 | 已发offer |
| `note` | String? | 备注 | 任意 |
| `unsuitableAt` | DateTime? | 标记不合适时间 | 不合适 |

### 3.2 状态枚举值

```prisma
model FollowUpRecord {
  status String @default("CONTACTING")
  // 合法值: CONTACTING | INTERVIEW_SCHEDULED | INTERVIEWED
  //        | OFFER_SENT | PENDING_ONBOARD | HIRED
  //        | RESIGNED | OFFER_REJECTED | INTERVIEW_CANCELLED
  //        | UNSUITABLE
}
```

无数据库级枚举约束 (SQLite 不支持)，合法性由应用层校验。

### 3.3 回退后字段清空策略

保持现有代码的清空逻辑（与 PRD 第五节"回退成功后，原状态对应的信息会被清空"一致）：

- 从「已入职」回退时：清空 `startDate`、`salaryRange`、`jobLevel`
- 进入「不合适」时写入 `unsuitableAt`，从「不合适」回退时清空 `unsuitableAt`
- 前端回退请求携带 `rejectReason: null`，清空拒绝原因

> 其他字段（如 `resignedAt`、`resignReason`）回退时保留，本次扩展不为新增的回退路径追加清空规则。
> 回退原因 `rollbackReason` 仅写入操作日志（便于审计），不落库为独立字段。

### 3.4 FollowUpLog 增强

回退操作日志格式：
```json
{
  "action": "ROLLBACK",
  "detail": "{\"from\":\"OFFER_SENT\",\"to\":\"INTERVIEWED\",\"reason\":\"误点击\"}"
}
```

### 3.5 历史数据迁移

`HIRED` 枚举值保持不变，仅前端 Tab 标签从"已录用"改为"已入职"。历史 `HIRED` 记录中的中间环节（已发offer/待入职）留空，不强制补全。

## 五、API 接口

### 5.1 PATCH `/api/follow-up/records/[id]` (核心变更)

统一处理**状态切换**和**内联编辑**。

**状态切换请求**：
```http
PATCH /api/follow-up/records/xxx
Content-Type: application/json

{ "status": "OFFER_SENT", "startDate": "2026-08-15" }
```

**内联编辑请求**：
```http
PATCH /api/follow-up/records/xxx
Content-Type: application/json

{ "interviewTime": "2026-08-20 14:00" }
```

**回退请求**：
```http
PATCH /api/follow-up/records/xxx
Content-Type: application/json

{ "status": "INTERVIEWED", "rollbackReason": "面试时间填写错误" }
```

**处理流程**：
1. 查询当前记录
2. 若 `body.status` 存在 → 调用 `validateTransition(currentStatus, targetStatus, body)`
3. 合法 → 更新字段 + 写入 `FollowUpLog`
4. 不合法 → 返回 400 `{ error: "不允许从 xxx 转换到 yyy" }`

**响应**：
```json
{
  "id": "xxx",
  "status": "OFFER_SENT",
  "startDate": "2026-08-15",
  ...
}
```

### 5.2 GET `/api/follow-up/records` (无结构变更)

已有 `recordStatus` 查询参数，前端传入新枚举值即可过滤对应 Tab。

### 5.3 不需要变更的端点

- `POST /api/follow-up/records` — 创建逻辑不变
- `DELETE /api/follow-up/records/[id]` — 删除逻辑不变
- `GET/POST /api/follow-up/tags` — 标签 CRUD 不变
- `POST /api/follow-up/export` — 导出不变
- `PATCH /api/follow-up/records/[id]` 内联编辑 (`interviewTime`, `note`, `contacted` 等) — 已有逻辑保持

### 6.3 操作列渲染逻辑

每条记录根据 `activeTab` 查找 `FOLLOW_UP_ACTIONS[activeTab]`，动态渲染：

- **正向按钮**：遍历 `forward[]`，点击打开对应弹窗
- **回退按钮**：若 `rollback[]` 非空，显示 `RotateCcw` 图标（`text-muted-foreground`）
- **取消跟进**：仅在 `CONTACTING` Tab 显示，保留现有逻辑


### 6.4 弹窗复用方案

| 操作 | 复用组件 | 说明 |
|------|---------|------|
| 预约面试 | 现有 ScheduleDialog (内联) | 不变 |
| 面试完成 | 现有面试结束弹窗 (内联) | 保留：可编辑维度评分/标签/备注后转为已面试 |
| 不合适 | `UnsuitableDialog` | `title="不合适"`，`targetStatus="UNSUITABLE"` |
| 取消面试 | `UnsuitableDialog` | `title="取消面试"`，`targetStatus="INTERVIEW_CANCELLED"` |
| 拒offer | `UnsuitableDialog` | `title="拒offer"`，`targetStatus="OFFER_REJECTED"` |
| 发offer | 现有 HireDialog (内联，需通用化) | 保留 `startDate`，title/目标状态可配置 |
| 接受offer | 同上 HireDialog | title="接受offer"，目标状态 PENDING_ONBOARD |
| 入职 | 同上 HireDialog | title="入职"，目标状态 HIRED |
| 离职 | 现有 ResignDialog (内联) | 不变 |
| 回退 | 现有回退弹窗 (内联) | 目标状态按当前状态动态生成；新增回退原因输入 |

**关键改造点**：
- **HireDialog**（现用于"录取"）：改为通用弹窗，`title`/确认按钮文案/目标状态可配置，复用于发offer、接受offer、入职三种场景；`startDate` 字段保留
- **UnsuitableDialog**：新增 `targetStatus` prop（默认 `UNSUITABLE`），复用于取消面试（`INTERVIEW_CANCELLED`）、拒offer（`OFFER_REJECTED`）
- **回退弹窗**：目标状态下拉按当前状态从 `ROLLBACK_TRANSITIONS` 动态生成；新增回退原因文本输入（必填，写入日志）
- **面试结束弹窗**：保留现有实现不变（维度评分/标签/备注编辑 + 转为已面试）

### 6.5 内联编辑

| 字段 | 可编辑 Tab | 组件 | 二次确认 |
|------|-----------|------|---------|
| `interviewTime` | 待面试 | `<input type="date">` 或 `<input type="datetime-local">` | 否 |

实现方式：在对应 `<td>` 内放置表单控件，`onChange`/`onBlur` 时调用 PATCH API。

## 八、开发规范

1. **状态枚举**：前端和后端均使用英文常量（如 `OFFER_SENT`），展示层通过 TABS / LABELS 映射为中文
2. **错误处理**：PATCH 返回明确的校验错误信息，前端 `toast.error()` 展示
3. **操作日志**：每次 PATCH 涉及 `status` 变更时，必须写入 `FollowUpLog`（含回退原因）
4. **代码风格**：遵循项目现有模式——常量定义在文件顶部，操作函数用 `handleXxx` 命名，UI 使用 Tailwind + shadcn/ui
5. **弹窗状态**：使用 `useState<{ open: boolean; ... }>()` 模式管理，与现有 `scheduleDialog`、`unsuitableDialog` 等一致

## 九、测试策略

### 端到端测试（Playwright MCP）

测试文件放入 `.playwright-mcp/` 目录，覆盖以下场景：

#### 正向流转
- [ ] 沟通中 → 预约面试 → 待面试（填写面试时间）
- [ ] 待面试 → 面试完成 → 已面试（可选备注）
- [ ] 已面试 → 发offer → 已发offer（填写入职时间）
- [ ] 已发offer → 接受offer → 待入职
- [ ] 待入职 → 入职 → 已入职
- [ ] 已入职 → 离职 → 已离职（填写离职时间+原因）

#### 拒绝/取消场景
- [ ] 沟通中 → 不合适
- [ ] 待面试 → 取消面试
- [ ] 已面试 → 不合适
- [ ] 已发offer → 拒offer
- [ ] 待入职 → 拒offer

#### 回退路径
- [ ] 已发offer → 回退到已面试
- [ ] 不合适 → 回退到已面试 / 沟通中
- [ ] 拒offer → 回退到待入职 / 已发offer
- [ ] 验证回退后原有数据保留

#### 内联编辑

## 十、部署流程

### 10.1 数据库变更

无需 SQL 迁移脚本。`status` 字段为字符串类型，无需 ALTER TABLE。新枚举值直接通过应用层校验生效。

### 10.2 部署步骤

1. **测试环境**：
   - `git pull` 拉取最新代码
   - `./dev.sh npx prisma generate`（无 schema 变更，但保持习惯）
   - `./dev.sh npm run build` 验证构建
   - 启动应用进行人工验证

2. **生产环境**：
   - 合并到 `release` 分支
   - PM2 重启：`pm2 restart hr-resume-system`

### 10.3 回滚方案

若新状态流转有问题：
1. 前端 `TABS` 和 `FOLLOW_UP_ACTIONS` 回退到旧版本（仅保留 6 个 Tab）
2. 新状态值（`OFFER_SENT` 等）在旧代码中不渲染对应 Tab，数据仍在数据库无丢失
3. 修复后重新上线

### 10.4 风险评估

| 风险 | 等级 | 缓解措施 |
|------|------|---------|
| 状态枚举值拼写错误 | 低 | 前后端共用 `TRANSITIONS` 常量类型检查 |
| 非法流转绕过校验 | 低 | `validateTransition` 在后端 PATCH 中强制校验 |
| 历史 HIRED 数据标签变更 | 低 | 值不变，仅前端标签映射修改 |
| 10 Tab 在小屏显示问题 | 低 | `overflow-x: auto` 横向滚动 |
