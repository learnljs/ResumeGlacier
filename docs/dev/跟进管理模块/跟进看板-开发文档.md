## 一、功能需求说明

### 1.1 模块构成

在 `app/resume/dashboard/page.tsx` 现有内容（指标卡 + 收取趋势）下方新增「跟进看板」区块，含三块统计 + 两组筛选：

| 部分 | 内容 | 数据口径 |
|---|---|---|
| 岗位多选 | 下拉多选，默认「全部岗位」 | 统计范围 = 所选岗位的全部投递；不传岗位 = 全部岗位（后端不过滤启用状态，含停用/已删除与 `unassigned` 占位评估） |
| 时间段选择 | 起止日期手动输入 + 周快捷（原生周输入 + 上一/下一周按钮），默认本周 | 作用于三块统计：状态卡 / 环形图 / 流转图均按所选时间段过滤 |
| 状态卡 ×10 | 沟通中/待面试/已面试/已发offer/待入职/已入职/已离职/拒offer/取消面试/不合适 | 当前快照：所选时间段内进入已筛选的投递中，当前处于各状态的投递数 |
| 是否联系上环形图 | 未尝试/已联系上/未联系上 占比与数量 | 当前快照：所选时间段内进入已筛选的「沟通中」投递的 `contacted` |
| 周报流转图 | 卡片节点图（7 正向节点 + 7 条流失分支） | 所选时间段批次的历史净流转（见 §四） |

**统计单位 = 投递**：一条 `FollowUpRecord`（对应唯一 `PositionEvaluation` = 简历 × 岗位）。同一候选人投多个岗位各计一次，独立统计。

**权限**：与数据概览页一致（系统无认证层，无额外控制）。

### 1.2 岗位选择规则

- 下拉选项 = 所有 `status = "active"` 的岗位（停用/已删除**不出现在下拉中**）；但「全部岗位」（不传 `positionIds`）统计时后端不过滤启用状态，停用/已删除岗位与 `unassigned` 占位评估的投递也会计入（见 §4.2）。
- 默认不选任何具体岗位 = 全部岗位（`MultiSelect` 空值语义）。
- 切换岗位后三块统计同时按新范围重新请求。

### 1.3 交互与刷新

- 打开页面 / 切换岗位 / 切换时间段：请求看板聚合接口（一次返回状态卡 / 环形图 / 流转图三块）。
- 手动刷新按钮：重新请求当前岗位 + 时间段的数据。
- 不做自动轮询（跟进操作低频，PRD「实时监控」由按需 + 手动刷新满足）。

### 1.4 非目标

- 状态卡点击跳转跟进管理页（PRD 未要求，后续可加）。
- 看板级权限/数据隔离。

## 二、关键决策记录（评审结论）

| # | 决策点 | 结论 | 理由 |
|---|---|---|---|
| 1 | 流转历史数据源 | `FollowUpLog` 加结构化列 `fromStatus/toStatus/transitionType`，配回填脚本 | 历史可追溯、查询可靠；SQLite `ADD COLUMN` 无需重建表；不引入新表 |
| 2 | 回退统计口径 | **净流转重放**：回退/复活撤销对应到达与流转线，只统计最终仍成立的 | 停留总和 = 批次总数，与状态卡自洽；PRD「停留 = 到达 − 流出」定义仅此口径成立 |
| 3 | REFOLLOW 语义 | 「不合适候选人复活」合法场景：复评候选池排除条件为 `status != 'UNSUITABLE'`，不合适者可回流、重新跟进重置为沟通中 | 不修改现有入口；重放按「整链退回沟通中」处理 |
| 4 | 批次圈定 | `PositionEvaluation.screenedAt` 落在所选时间段（为空回退 `createdAt`；含手动占位评估，不特判） | 以「首次进入已筛选」为批次语义，贴合「已筛选」批次入口定义 |
| 5 | API 形态 | 单一聚合接口 `GET /api/dashboard/follow-up-board`，一次返回三块数据（statusCards / contactRing / flow） | 同一参数快照、切换时一次请求；口径差异在服务端内部并行计算，前端不感知 |
| 6 | 刷新策略 | 按需加载 + 手动刷新按钮 | 简单够用 |
| 7 | 环形图实现 | recharts（项目已有，与 `PositionTrendCompareChart` 一致） | 流转图为手写 flex 布局（无图表库支持卡片节点形态） |
| 8 | 岗位多选 | 复用 `components/ui/multi-select.tsx`（`showSelectAll`，空值 = 全部） | 已有组件，语义匹配 |

## 三、数据模型变更

### 3.1 FollowUpLog 新增列

```prisma
model FollowUpLog {
  id               String         @id @default(cuid())
  followUpRecordId String
  action           String
  detail           String?
  fromStatus       String?        // 新增：流转前状态；"SCREENED" 表示从已筛选进入跟进；null = 未知（降级）
  toStatus         String?        // 新增：流转后状态
  transitionType   String?        // 新增："enter" | "forward" | "rollback" | "reset"；null = 非状态变更类日志
  createdAt        DateTime       @default(now())
  followUpRecord   FollowUpRecord @relation(fields: [followUpRecordId], references: [id], onDelete: Cascade)
}
```

`transitionType` 语义：

| 值 | 含义 | 重放处理 |
|---|---|---|
| `enter` | 从「已筛选」进入跟进（`fromStatus = "SCREENED"`） | 记入到达与流转线 |
| `forward` | 状态机正向流转 | 记入到达与流转线 |
| `rollback` | 状态机回退 | 撤销对应的到达与流转线 |
| `reset` | REFOLLOW 复活重置（`toStatus = "CONTACTING"`，`fromStatus` 可为 null） | 整链退回沟通中（见 §4.3） |

变更步骤：修改 `prisma/schema.prisma` -> `./dev.sh npx prisma db push` -> `./dev.sh npx prisma generate`。无迁移文件（项目约定直接 `db push`）。

### 3.2 写入点改造清单（5 处）

| 文件 | 位置 | 改造 |
|---|---|---|
| `app/api/follow-up/records/route.ts` | POST 创建分支（`CREATE`/`UNSUITABLE` 日志） | `fromStatus: 'SCREENED', toStatus: effectiveStatus, transitionType: 'enter'` |
| `app/api/follow-up/records/route.ts` | POST 已有记录分支（`REFOLLOW`/`UNSUITABLE`） | `fromStatus: existing.status, toStatus: effectiveStatus, transitionType: effectiveStatus === 'UNSUITABLE' ? 'forward' : 'reset'` |

## 四、统计口径与重放算法

### 4.1 状态卡 / 环形图（当前快照）

- **岗位归属口径**：投递的岗位 = `evaluation.positionId`（不是 `resume.positionId`）；`evaluationId` 为空的历史孤儿记录无法直接归属岗位，按 `resume.positionId` 兜底归属并计入看板（聚合接口内状态统计与流转图同口径，与 §4.2 批次圈定一致）。
- **时间段口径**：三块统计均按所选时间段过滤——投递的进入已筛选时间（`evaluation.screenedAt`，为空回退 `createdAt`；孤儿记录按 `FollowUpRecord.createdAt`）落在 `[from, to]`（含首尾）内才计入。
- 状态卡：上述范围内 `FollowUpRecord` `groupBy status`，10 个状态各返回计数（缺失补 0）。
- 环形图：上述范围内 `status = 'CONTACTING'` 的记录 `groupBy contacted`（`NOT_CONTACTED`/`CONTACTED`/`CONTACT_FAILED`）。

### 4.2 时间段批次圈定（流转图）

```
批次 = PositionEvaluation where:
  positionId ∈ 所选岗位                     // 选中具体岗位时精确过滤；不传 positionIds = 全部岗位（后端不过滤启用状态）
  screenedAt ∈ [from, to + 1d)             // 进入已筛选时间；screenedAt 为空回退 createdAt
```

- **时区注意**：解析 `from`/`to` 必须按本地时区构造 `new Date(y, m-1, d)`；`new Date('YYYY-MM-DD')` 在 Node 按 UTC 午夜解析，东八区会把边界偏移到当日 08:00，漏掉当日 0~8 点的评估（`lib/services/date-utils.ts` 的 `parseBoardDateRange` 已按本地时区处理，并校验月份回绕 / 闰年 / `from <= to`）。
- `positionId = 'unassigned'` 的占位评估（未分配岗位时创建，见 `app/api/follow-up/records/route.ts`）：选中具体岗位时因不匹配所选岗位而不计入；「全部岗位」（不传 `positionIds`）时会被计入。
- **孤儿兜底**：`evaluationId` 为空的历史 `FollowUpRecord` 无投递关联，按「`resume.positionId` 匹配岗位 + `createdAt` 落入时间段」单独圈定，计入批次总数（聚合接口内两路统计同口径）。
- 流转线统计范围为该批投递的**全部**历史事件（不限于所选时间段内发生），以当前时刻重放结果为准。

### 4.3 净流转重放算法

对批次内每条投递（有 `FollowUpRecord` 的），按 `FollowUpLog.createdAt` 升序重放：

```
reached: Set<status>          // 最终仍成立的到达
lines:   Map<"A->B", bool>    // 最终仍成立的流转线

for 事件 in 时间顺序:
  enter   SCREENED -> B:  reached.add(B);  lines.set("SCREENED->B", true)
  forward A -> B:        reached.add(B);  lines.set("A->B", true)
  rollback B -> A:       reached.delete(B); lines.delete("A->B")
  reset   ? -> CONTACTING:  // REFOLLOW 复活：整链退回沟通中
                         reached = {CONTACTING}
                         lines   = {"SCREENED->CONTACTING"}
```

要点：

- 回退只撤销**相邻**那对到达/线；回退后再次正向则重新生效（`reached`/`lines` 为集合语义，天然去重，「多次到达只算一次」）。
- `reset` 将该投递恢复到刚进入跟进的状态：撤销沟通中之后的全部到达与线（含之前走到的不合适终点），与「复活重新开始一轮」的业务语义一致。
- `rollback` 与 `reset` 的区别：`rollback` 是状态机内单步回退（日志有明确 from）；`reset` 是 REFOLLOW 强制重置（from 可能未知，但重放不需要 from）。
- **图外边防御**：正向流转仅可能产生 §4.4 边集内的线（状态机保证）；若历史脏数据产生边集外的线（如路径 3 直改 UNSUITABLE），该线不落入任何预定义边则忽略并计数上报。
- **降级行**：`fromStatus=null` 的 forward 行（回填无法确定来源）跳过、计数上报；日志全部无法解析的投递不计入任何节点/线（守恒校验对此类记录存在预期偏差，见 §六）。
- **删除跟进记录**：日志级联删除，该投递自动回到「已筛选停留」，重放无需特判；之后重新跟进会产生新的 `enter` 事件。

### 4.4 流转图固定边集（11 节点 / 13 条线）

```
正向 7 节点：SCREENED(已筛选) -> CONTACTING -> INTERVIEW_SCHEDULED -> INTERVIEWED
             -> OFFER_SENT -> PENDING_ONBOARD -> HIRED

流失/终止 7 条边：
  SCREENED        -> UNSUITABLE          （已筛选 -> 不合适）
  CONTACTING      -> UNSUITABLE          （沟通中 -> 不合适）
  INTERVIEW_SCHEDULED -> INTERVIEW_CANCELLED
  INTERVIEWED     -> UNSUITABLE
  OFFER_SENT      -> OFFER_REJECTED
  PENDING_ONBOARD -> OFFER_REJECTED
  HIRED           -> RESIGNED
```

节点「到达」= 该节点在 `reached` 中的投递数；「停留」= 到达 − 流出（流出 = 从该节点出发的所有有效线之和）。已筛选节点到达 = 批次总数，停留 = 尚未跟进数。

守恒校验（验证用）：各正向节点停留数之和 + 流入终点（不合适/取消面试/拒offer/已离职）线数之和 = 批次总数。

## 五、接口文档

单一聚合接口，一次请求返回三块数据（状态卡 / 环形图 / 流转图），参数：

| 参数 | 类型 | 说明 |
|---|---|---|
| `positionIds` | string（可选） | 逗号分隔岗位 id；缺省/空 = 全部岗位（后端不过滤启用状态，含停用/已删除与 `unassigned` 占位评估）。传入的 id 按岗位精确过滤（下拉仅展示启用中岗位，故实际传入均为启用中） |
| `from` / `to` | string | 时间段起止日期 `YYYY-MM-DD`（含首尾），必填 |

### GET /api/dashboard/follow-up-board

**位置**：`app/api/dashboard/follow-up-board/route.ts`

**作用**：状态卡 + 是否联系上环形图 + 批次总数 + 周报流转图（7 正向节点 + 7 条流失分支）。

**响应**：

```jsonc
{
  "statusCards": [                    // 固定 10 项，按状态枚举顺序（缺失补 0）
    { "status": "CONTACTING", "count": 48 },
    { "status": "INTERVIEW_SCHEDULED", "count": 12 }
    // ... INTERVIEWED / OFFER_SENT / PENDING_ONBOARD / HIRED / RESIGNED
    //     / OFFER_REJECTED / INTERVIEW_CANCELLED / UNSUITABLE
  ],
  "total": 48,                        // 范围内已跟进（有 FollowUpRecord）的投递数 = 状态卡之和
  "contactRing": {                    // 仅范围内「沟通中」投递
    "total": 48,
    "segments": [
      { "contacted": "NOT_CONTACTED", "count": 10 },  // 未尝试
      { "contacted": "CONTACTED", "count": 26 },      // 已联系上
      { "contacted": "CONTACT_FAILED", "count": 12 }  // 未联系上
    ]
  },
  "flow": {
    "from": "2026-08-17",             // 回显所选起始日期
    "batchTotal": 60,                 // 范围内批次总数（含尚未跟进的投递与孤儿兜底）
    "nodes": [                        // 正向 7 节点，按顺序
      { "status": "SCREENED", "reached": 60, "stayed": 12 }
      // ... CONTACTING / INTERVIEW_SCHEDULED / INTERVIEWED
      //     / OFFER_SENT / PENDING_ONBOARD / HIRED
    ],
    "branches": [                     // 流失/终止 7 条边
      { "from": "SCREENED", "to": "UNSUITABLE", "count": 2 }
      // ...
    ]
  }
}
```

**错误**：`from`/`to` 缺失、非 `YYYY-MM-DD` 或 `from > to` 返回 400；无投递时各计数为 0（不报错）。

**实现**：路由内 `computeStatusStats`（状态卡 + 环形图，`groupBy` 聚合）与 `lib/services/follow-up-board-flow.ts` 的 `getFollowUpBoardFlow(positionIds, from, to)`（日志净重放）在同一参数快照下并行计算后合并返回（数据量级：日志千条内，SQLite 毫秒级，无需缓存/物化）；时间范围解析复用 `lib/services/date-utils.ts` 的 `parseBoardDateRange`。

## 六、回填脚本

**文件**：`scripts/backfill-follow-up-transitions.ts`（新增，`./dev.sh npx tsx` 执行）

**范围**：`FollowUpLog` 中 `transitionType IS NULL` 的行（幂等，可重复执行）。

**规则**：

| action | 解析 | 写入 |
|---|---|---|
| `STATUS_CHANGE` / `INTERVIEW_END` / `ROLLBACK` | 按 detail 首行匹配两种历史格式（见下方格式表）；再兜底尝试 JSON 解析（状态 v2 设计稿曾定义 `{"from":…,"to":…}` 格式） | `forward`（`ROLLBACK` 为 `rollback`；`INTERVIEW_END` 的 to 固定为 INTERVIEWED） |
| `STATUS_CHANGE`（detail 含「定时扫描到期离职」） | scheduler 自动离职日志，无「状态变更：」格式；已核实该路径前置状态必为 `HIRED`（`scheduler.ts:210`） | `forward`，`HIRED -> RESIGNED` |
| `CREATE` / `BATCH_CREATE` | - | `enter`，`SCREENED -> CONTACTING` |
| `UNSUITABLE` | 判断方式：取该记录按 `createdAt` 排序的**最早一条日志**，若其 action 为 `UNSUITABLE` 则视为创建即不合适（不用时间容差） | 首条：`enter`，`SCREENED -> UNSUITABLE`；非首条：`toStatus='UNSUITABLE'`，`fromStatus=null`（来源未知） |
| `REFOLLOW` | - | `reset`，`toStatus='CONTACTING'`，`fromStatus=null` |
| 其他（`NOTE_CHANGE`、`TAG_CHANGE` 等） | - | 跳过（保持 null） |

**历史日志格式与标签变体**（中文反查英文枚举必须覆盖全部）：

| 时期 | detail 格式 | 标签差异 |
|---|---|---|
| 2026-04 ~ 06-16 | `状态从「X」变更为「Y」` | 旧枚举仅 `ACTIVE`/`UNSUITABLE`：**跟进中**(=ACTIVE，记录已由 `migrate-followup-status.ts` 迁移为 CONTACTING)、**不适合** |
| 2026-06-16 ~ 状态v2 | `状态变更: X -> Y` | **已录用**(=HIRED，v2 后改叫已入职)、不合适 |
| 状态 v2 至今 | `状态变更: X -> Y` | 现行 10 状态标签 |

正则：`/^状态变更: (.+) (?:→|->) (.+)/`（兼容全角/半角箭头）与 `/^状态从「(.+)」变更为「(.+)」/`（匹配首行即可，detail 为多行文本）。

**降级与兜底**：

- 解析失败的行保持 null 并打印 id 清单（含标签映射不到、格式不认识两种情况）。
- `fromStatus=null` 的 forward 行重放时**跳过并计数上报**（终点无节点卡，分支卡显示的是线数，无法归属线则整行无意义；该路径前端不可达，历史量预期为 0）。
- **批次守恒偏差**：若某投递的日志全部解析失败，它在流转图中不计任何节点/线，导致「批次总数 > 图上各数之和」。脚本输出此类记录数量供评估规模，不做虚构合成。
- 运行模式：默认 **dry-run**（只统计预览不写库），加 `--write` 才落库；幂等，可重复执行。

> 跟进状态 v2 之前的旧日志可能不含「状态变更：」格式，属预期内降级，不计为脚本缺陷。

### 7.2 交互逻辑

- 岗位选择：`MultiSelect`（`showSelectAll`），空值 = 全部岗位 -> 请求不带 `positionIds`。
- 时间段选择（`components/resume/BoardPeriodPicker.tsx`）：起止日期手动输入（`YYYY-MM-DD`，含首尾）+ 周快捷（原生 `week` 输入 + 上一/下一周按钮，选择后一键回填起止日期框）；默认本周（周一~周日）；周快捷只负责回填，不锁定日期类型。
- 切换岗位 / 时间段：请求聚合接口（一次返回三块数据），`reqIdRef` 请求序号丢弃过期响应；手动刷新按钮同。
- 请求期间流转图与状态卡显示加载态；失败 toast（sonner）。
- 不做原型底部的动态叙述文字（flowNote「已筛选 30 条投递中：28 进入沟通中…」），保留固定图例即可--叙述内容与图上数字重复，拼接文案维护成本高于价值。

### 7.3 样式要点（对齐原型）

- 状态卡：顶部 3px 主题色条，数字 26px；「不合适」数字用警示色（原型 `--coral`）。
- 流转图：7 正向卡与 7 分支卡两行 flex、同列对齐（同构固定宽 80px + 空位 `flex-1`），卡片三行（状态名 / 到达数 / 停留），正向卡间 `->` 箭头；分支卡用竖线 + ▼ + 流出数量连接，不合适类红色调、offer 类金色调；`overflow-x: auto` 横向滚动（min-width 700px）；底部图例（`->` 正向推进 / `▼` 流失终止 / 下方数字为流出数量）。
- 响应式：窄屏（<1180px）环形图与流转图上下堆叠。

## 九、验证要点（对齐 PRD §五）

1. 岗位多选默认全部；停用/已删除岗位不出现；多选合并统计、同候选人多投递各计一次；切换后三块同刷。
2. 10 状态卡计数 = 所选时间段内进入已筛选、当前处于各状态的投递数。
3. 环形图仅统计所选时间段内进入已筛选的沟通中投递，三段占比 + 绝对数，中心显示沟通中总数。
4. 流转图 11 节点齐全；时间段选择器默认本周，支持手动起止日期 / 周快捷 + 上一/下一周；所选时间段内无投递时各数显示 0。
5. 净流转口径专项用例：
   - 回退后流转：沟通中->待面试->回退->不合适 => 待面试不计、沟通中->不合适计 1；
   - 复活重置：不合适 ->（复评重跟）沟通中 -> 待面试 => 不合适线被撤销、待面试计 1；
   - 守恒：各节点停留和 + 终点线和 = 批次总数。
6. 批次归属：复评（原地更新）不改变投递所在批次；孤儿记录（evaluationId 为空）按 resume.positionId 兜底归属并计入批次总数。
