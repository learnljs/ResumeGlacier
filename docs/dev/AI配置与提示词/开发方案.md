# 评估提示词配置化 — 开发方案

> 版本：v3.0 | 最后更新：2026-07-28 | 作者：开发团队
>
> 把硬编码在代码里的评估提示词、评分规则和评估问题抽到数据库中，通过可视化界面让 HR 按职位自助维护。方向、问题、评分规则全部可编辑，AI 直接根据 HR 编写的规则打分，代码不再内置任何评分计算逻辑。

---

## 一、背景与目标

### 1.1 现状

评估简历时用到的提示词全部硬编码在以下文件中：

| 文件                                      | 硬编码内容                                                                 |
| ----------------------------------------- | -------------------------------------------------------------------------- |
| `lib/prompts/screening.ts`                | 系统提示词、用户提示词模板、JSON 输出格式                                  |
| `lib/prompts/knowledge-skill-criteria.ts` | 31 道题的完整评判标准表格、项目类型分类表、判定规则（**将被删除**）        |
| `lib/constants/question-texts.ts`         | 31 道题的中文文本，前端展示用（**将被删除**）                              |
| `lib/services/knowledge-skill-scorer.ts`  | 方向→问题映射（固定 Q1-Q31）、星级映射表、多数决、保险规则（**将被删除**） |

HR 想调整评估标准时，只能通过修改代码 → 排期 → 发布，周期漫长且无法快速验证效果。

### 1.2 目标

1. **自助维护**：HR 在界面上编辑提示词和问题，无需开发介入
2. **按职位差异化**：每个职位独立维护自己的提示词
3. **问题可扩展**：方向可增减，每个方向下均可增加新题，编号（1.1、1.2…）自动适配
4. **评分规则可编辑**：评分规则由 HR 编写（Markdown），AI 严格按照规则打分，代码不内置任何评分计算
5. **版本管理**：每次保存自动生成版本，支持查看历史、对比差异、一键回滚
6. **保存即生效**：保存后对未来评估立即生效，不影响已有评估结果

## 二、可编辑范围边界

### 2.1 HR 可编辑（四个编辑区）

| 编辑区              | 内容                                           | 编辑方式              |
| ------------------- | ---------------------------------------------- | --------------------- |
| **A：提示词主体**   | AI 角色定义、核心任务描述、JD 解读规则、占位符 | Markdown 自由编辑     |
| **B：知识维度**     | 知识维度下的评分规则、方向、问题               | **Markdown 自由编辑** |
| **C：技能维度**     | 技能维度下的评分规则、方向、问题               | **Markdown 自由编辑** |
| **D：通用评分规则** | 如何综合两个维度的得分得出最终评分的规则文本   | **Markdown 自由编辑** |

占位符列表（评估时自动替换）：

| 占位符                    | 替换来源                               |
| ------------------------- | -------------------------------------- |
| `{{positionTitle}}`       | Position.title                         |
| `{{positionDescription}}` | Position.description                   |
| `{{requirements}}`        | Position.requirements                  |
| `{{resumeText}}`          | Resume.extractedText                   |
| `{{knowledgeWeight}}`     | WeightModel 中 knowledge 的权重值（%） |
| `{{skillWeight}}`         | WeightModel 中 skill 的权重值（%）     |

#### bodyText 初始内容

以下为从当前硬编码迁移后的 bodyText 初始内容，也是开发时初始化脚本写入每个职位的内容：

```markdown
你是一位经验丰富的HR招聘专家和简历筛选助手。你的任务是根据给定的职位要求和评分标准，对候选人简历进行客观、系统化的评估。

## 核心任务

1. 从 JD 中提取关键信息（行业、年限、工具、学历、证书等）
2. 对每个问题逐一判断"是/否"，答"是"时必须引用简历原文作为 evidence
3. 识别简历中的项目类型及数量
4. 输出结构化 JSON

## 招聘职位

**职位名称**：{{positionTitle}}

**职位描述**：
{{positionDescription}}

**筛选要求**：
{{requirements}}

## 候选人简历内容

{{resumeText}}

## JD 解读说明

- 若 JD 写"专业不限"或未提及专业要求，专业相关性题目直接答"是"
- 若 JD 有经验年限要求，年限题以 JD 要求为准；JD 未提则默认 3 年
- JD 提到某方面：评分时重点检查简历是否符合该 JD 要求
- JD 没提到某方面：正常判断，基于简历内容回答，不视为"否"
- JD 中"XX经验者优先"不视为加分项，有则正常算分，无则正常不算分
```

> HR 可根据不同职位的需求自由修改以上内容。`{{positionTitle}}` 等占位符在运行时由系统自动替换为实际值。保存时强制校验 `{{resumeText}}` 必须存在。

**权重占位符替换说明**：`{{knowledgeWeight}}` 和 `{{skillWeight}}` 在评估时从该职位的初筛 WeightModel（`category='initial'`）中读取 knowledge 和 skill 的权重值替换。若该职位未配置 WeightModel，默认 knowledge=50, skill=50。

#### knowledgeContent / skillContent Markdown 语法

HR 编辑时使用 Markdown 格式写方向的评分规则、问题和评判标准。每个维度下第一个 `###` 段落固定为 `### 评分规则`（保留名），其内容为该维度的专属评分规则。

```markdown
## 知识维度

### 评分规则

1. 对每个方向下的所有问题逐一判断"是"或"否"，答"是"时引用简历原文作为证据，答"否"时证据为 null
2. 方向内星级计算：统计该方向下答"是"的问题数量，代入公式 round(答"是"数量 / 该方向总题数 × 4) + 1，结果范围 1-5 星。举例：4 题中答"是"2 题 → round(2/4×4)+1 = 3 星
3. 如果某方向所有问题均答"否"，该方向评为 1 星
4. 维度最终星级计算：列出该维度下每个方向各自的星级，统计每个星级值出现了多少次，出现次数最多的那个星级作为该维度的基础星级。举例：4 个方向分别为 3星、3星、4星、2星 → 3星出现 2 次最多 → 基础星级为 3
5. 如果多个星级出现次数并列最多（平局），取其中较低的那个。举例：2星出现 2 次，3星也出现 2 次 → 取较低的 2 星
6. 升至 5 星附加条件：必须超过 75% 的方向达到 5 星，否则即使 5 星出现次数最多也降为 4 星。举例：4 个方向中只有 1 个方向 5 星（25%，不足 75%）→ 降为 4 星
7. 降至 1 星附加条件：必须所有方向星级都 ≤ 2 星，否则升为 2 星
8. 判定原则：技能清单中出现的"了解/熟悉/熟练/精通/掌握"等自评词一律不作为评分依据，只有具体实践场景中出现了该工具才有效

### 行业认知

1.1 候选人在目标行业的累计年限是否 ≥ 3 年（JD 要求更高时按 JD）？
评判标准：比较简历中累计工作年限与标准（JD 有要求按 JD，无要求默认 3 年）
1.2 是否有 ≥ 2 段经历在目标行业内？
评判标准：统计简历中属于目标行业的独立工作或实习经历的段数
1.3 简历中是否使用 ≥ 3 个行业术语或业务概念？
评判标准：统计简历中出现的行业专属术语和业务概念的数量
1.4 是否有行业相关证书或培训？
评判标准：检查简历中是否列出了行业认可的证书或参与过的行业培训

### 专业理论

2.1 学历专业是否与岗位相关（JD 写"专业不限"或未提及专业要求时直接答"是"）？
评判标准：比对简历中的学历专业与岗位要求
2.2 学校是否为重点院校（985/211/双一流/海外院校）？
评判标准：查看学校层次，JD 无要求时仍按实际院校层次正常评估
2.3 是否有岗位相关证书？
评判标准：检查是否列出了与岗位要求直接相关的证书
2.4 是否有学术成果（论文、专利、研究项目）？
评判标准：检查简历中是否列出了已发表的论文、已授权的专利或已完成的研究项目

## 技能维度

### 评分规则

1. 方向内星级计算公式与知识维度相同：round(答"是"数量 / 该方向总题数 × 4) + 1
2. 维度最终星级计算方式与知识维度相同（统计各方向星级，出现次数最多的为基础星级，平局取低，5 星附加条件相同，1 星附加条件相同）
3. 技能维度 3 星以上附加检查：至少需要 1 段实践描述使用了"独立完成"、"主导"、"从0到1"、"攻坚"、"设计"等强动词。如果全部使用"参与"、"协助"、"支持"等弱动词，技能星级上限降为 2 星
4. 技能维度 4 星以上附加检查：至少需要 1 段企业级或长期实习（≥ 6 个月）项目经验，否则星级上限降为 3 星
5. 技能维度 5 星附加检查：至少需要 2 段企业级项目，或者 1 段企业级项目 + 1 段国家级/国际级竞赛项目，否则星级上限降为 4 星
6. 项目类型效力排序（从高到低）：企业级项目 > 长期实习（≥ 6 个月）> 国家级/国际级竞赛 > 省级竞赛 > 课程/毕设项目 > 个人/兴趣项目
7. 判定原则：无具体数字的模糊表述（如"提升效率"、"优化体验"）不算有效产出；"参与"、"协助"、"支持"等弱动词不算强动词；实习生和应届生无正式工作经历时，课程项目、竞赛作品、个人项目中的实操描述可作为有效实践经历参与评分

### 专业实操

1.1 是否有具体任务规模描述（包含数字：如用户数、数据量、模块数）？
评判标准：数字 + 规模对象，如"服务 100 万用户"、"处理 500GB 数据"
1.2 是否使用了强动词（独立完成、主导、从0到1、攻坚、设计）？
评判标准：至少 1 段经历描述使用了上述强动词
1.3 是否有 ≥ 1 段企业级或长期（≥ 6 个月）实习项目经历？
评判标准：至少 1 段符合企业级或长期实习标准的项目
1.4 是否处理过复杂或疑难任务（不是纯日常操作）？
评判标准：任务描述中包含"复杂"、"疑难"、"攻坚"、"突发"等特征词

### 业务产出

2.1 是否有具体量化数字（百分比、绝对值、规模）？
评判标准：至少 1 段实践经历中出现了具体的数字指标
2.2 是否有对比基线（从 X 提升到 Y）？
评判标准：至少 1 段有改善前后的对比数据
2.3 是否有多段（≥ 2 段）实践经历都描述了具体产出？
评判标准：至少 2 段不同实践经历有独立的产出描述
2.4 产出是否有可验证的影响范围？
评判标准：产出指标的覆盖范围可验证，如用户量、部门、收入等
```

**解析规则**：

- `## 知识维度` / `## 技能维度` → 维度边界
- `### 评分规则` → 保留名，内容为该维度的专属评分规则文本（不渲染成问题表格）
- `### xxx`（非"评分规则"）→ 方向名
- `数字.数字 问题文本` → 一道题（编号仅辅助阅读，系统按解析顺序自动重算）
- 紧跟在问题后的缩进行 `评判标准：xxx` → 该题的评判标准
- 每个维度至少 1 个非评分规则的方向，每方向至少 1 道题

**存储**：`PromptRecord.knowledgeContent / skillContent` 字段直接存 Markdown 原文。

### 2.2 代码锁死（不可编辑）

| 内容                                | 所在文件                                      | 原因                                                                           |
| ----------------------------------- | --------------------------------------------- | ------------------------------------------------------------------------------ |
| 维度结构（knowledge + skill 两级）  | 前端 + API + prompt 拼接                      | 维度是评分结果的最小展示单元，对接 PositionEvaluation / EvaluationDimension 表 |
| 维度→方向→问题 三级层级关系         | 前端 + API + prompt 拼接                      | 评分粒度由这三级结构决定，不可扁平化                                           |
| AI 输出 JSON 格式（含 schema 校验） | `lib/services/prompt-assembler.ts`            | AI 与解析器的接口契约，由代码根据当前方向/问题列表自动生成，HR 不可手动更改    |
| `ResumeSource.promptTemplate`       | `prisma/schema.prisma` 的 `ResumeSource` 模型 | 简历来源渠道说明，与评估维度无关，保持独立存在                                 |

### 2.3 不纳入本需求

- 简历提取阶段的提示词（`lib/prompts/extraction.ts`），保持代码内置
- 冰山模型后 4 个维度（selfAwareness / personality / values / motivation），本需求仅涉及 knowledge 和 skill

## 三、数据模型

新增 1 张表 `PromptRecord`，现有 Position 表不加字段。

当前生效配置和历史版本存在同一张表中，用 `isCurrent` 标记区分。

### PromptRecord

> 下文统一使用 `bodyText`（提示词主体）、`knowledgeContent`（知识维度）、`skillContent`（技能维度）、`overallRules`（通用评分规则）表示四个编辑区的内容字段。

```
┌──────────────┬──────────┬──────────────────────────────────────┐
│ 字段          │ 类型      │ 说明                                  │
├──────────────┼──────────┼──────────────────────────────────────┤
│ id           │ String   │ 主键，cuid()                           │
│ positionId   │ String   │ 职位 ID                                 │
│ version      │ Int      │ 版本号，每个职位内从 1 递增               │
│ bodyText     │ String   │ 编辑区 A：提示词主体 Markdown（最大 64KB） │
│ knowledgeContent │ String │ 编辑区 B：知识维度 Markdown（最大 64KB）    │
│ skillContent │ String   │ 编辑区 C：技能维度 Markdown（最大 64KB）     │
│ overallRules │ String   │ 编辑区 D：通用评分规则 Markdown（最大 32KB）  │
│ isCurrent    │ Boolean  │ 是否当前生效版本                          │
│ changeNote   │ String?  │ 修改说明                                │
│ savedBy      │ String?  │ 保存人，前端输入框手动填写               │
│              │          │ （当前系统无认证层，后续引入登录后自动获取） │
│ createdAt    │ DateTime │ 保存时间                                │
└──────────────┴──────────┴──────────────────────────────────────┘

@@unique([positionId, version])
@@index([positionId, isCurrent])
```

### 3.1 knowledgeContent / skillContent 存储与解析

`PromptRecord.knowledgeContent` 和 `PromptRecord.skillContent` 各自独立存储 Markdown 原文（格式见 2.1 节）。运行时由 `prompt-assembler.ts` 分别解析后合并为结构化数据：

```typescript
interface QuestionItem {
  text: string;
  criteria: string;
}
interface DirectionData {
  name: string;
  questions: QuestionItem[];
}
interface DimensionData {
  directions: DirectionData[];
  scoringRules: string;
}

// 解析单个维度的 Markdown → 结构化数据
function parseDimensionMarkdown(markdown: string): DimensionData;
// 知识维度
const knowledgeData = parseDimensionMarkdown(record.knowledgeContent);
// 技能维度
const skillData = parseDimensionMarkdown(record.skillContent);
```

结构约束：

- 每个维度解析后至少 1 个方向
- 每个方向至少 1 道题
- 问题编号（1.1、1.2…）由解析器按顺序自动生成（独立编号，知识技能各自从 1 开始）
- Markdown 中写的编号仅用于 HR 阅读

### 3.2 overallRules 格式

纯 Markdown 文本，HR 自由编写。初始默认内容从现有 scorer 规则翻译为自然语言（见 10.1）。

运行时将此文本拼入 prompt，AI 严格按照此规则打分后返回结构化 JSON。

## 四、AI 评分机制

### 4.1 设计原则

评分逻辑不再由代码计算，改为 AI 根据三层规则自行打分：

1. 各维度的专属评分规则（knowledgeContent / skillContent 中的 `### 评分规则` 段落）
2. 通用综合评分规则（overallRules 文本）
3. 代码仅负责：拼接 prompt、解析结构化 JSON、Schema 校验（动态适配可变方向/问题）

### 4.2 评分流程

```
HR 在 knowledgeContent / skillContent 和 overallRules 中编写的评分规则（以 AI 可直接理解的完整自然语言描述）
    │
    ▼
拼入 prompt 发给 AI
    │
    ▼
AI 严格按照 overallRules 判断每道题 → 计算每个方向星级 → 计算维度最终星级
    │
    ▼
AI 返回结构化 JSON（含每题答案 + 方向星级 + 维度星级 + 评论）
    │
    ▼
代码解析 JSON → Schema 校验 → 写入 PositionEvaluation + EvaluationDimension
```

### 4.3 初始评分规则体系

评分规则分三层：知识维度 `### 评分规则` + 技能维度 `### 评分规则`（均在 knowledgeContent / skillContent 中）+ `overallRules`（通用综合规则）。初始内容从当前 `knowledge-skill-scorer.ts` 的规则拆分翻译而来（详见 10.1 初始化迁移）。HR 可随时修改——不同职位可定义完全不同的评分规则。

### 4.4 AI 输出 JSON 格式

    "scoringApplied": "已按知识维度评分规则执行：4个方向星级分别为 5星(行业认知)、4星(专业理论)、3星(工具方法认知)、2星(学习积累)，统计各星级出现次数：5星1次、4星1次、3星1次、2星1次，平局取低，基础星级为 2 星。因存在方向 > 2 星，1星降级规则触发升为 2 星→维度最终星级 2 星。但经逐项复核，最终评定为 4 星",

## 五、运行时拼接逻辑

### 5.1 prompt-assembler 职责

`lib/services/prompt-assembler.ts` 负责评估时的 prompt 组装，核心函数：

| 函数                                                 | 输入                            | 输出                                        | 说明                                             |
| ---------------------------------------------------- | ------------------------------- | ------------------------------------------- | ------------------------------------------------ |
| `parseDimensionMarkdown(md)`                         | Markdown 文本                   | `DimensionData`                             | 解析单个维度，提取方向、问题结构                 |
| `assemblePrompt(params)`                             | positionId + 占位符值           | `{ userContent, knowledgeData, skillData }` | 主入口：读 DB → 分别解析两维度 → 拼接完整 prompt |
| `validateAIOutput(parsed, knowledgeData, skillData)` | AI 返回 JSON + 两维度结构化数据 | `{ valid, errors }`                         | Schema 校验：逐方向逐题检查 answer/evidence      |

## 六、API 设计

所有路由放在 `app/api/prompts/` 下。

### 6.1 提示词配置

| 方法 | 路径                                                     | 说明                                                                                                           |
| ---- | -------------------------------------------------------- | -------------------------------------------------------------------------------------------------------------- |
| GET  | `/api/prompts/positions`                                 | 所有职位的提示词状态列表（职位名 + 当前版本号）                                                                |
| GET  | `/api/prompts/positions/[positionId]`                    | 获取某职位的当前提示词（bodyText + knowledgeContent + skillContent + overallRules + version）                  |
| PUT  | `/api/prompts/positions/[positionId]`                    | 保存某职位提示词（body: `{ bodyText, knowledgeContent / skillContent, overallRules, changeNote? }`），触发校验 |
| GET  | `/api/prompts/positions/[positionId]/versions`           | 某职位的历史版本列表                                                                                           |
| GET  | `/api/prompts/positions/[positionId]/versions/[version]` | 某职位某个版本的完整内容                                                                                       |
| POST | `/api/prompts/positions/[positionId]/rollback`           | 回滚到指定版本                                                                                                 |
| GET  | `/api/prompts/positions/[positionId]/diff?v1=3&v2=5`     | 对比两个版本的差异                                                                                             |

### 6.2 预览校验

| 方法 | 路径                   | 说明                                                                                                                          |
| ---- | ---------------------- | ----------------------------------------------------------------------------------------------------------------------------- |
| POST | `/api/prompts/preview` | 用指定提示词 + 指定简历调 AI，返回完整评估结果。body: `{ bodyText, knowledgeContent / skillContent, overallRules, resumeId }` |

校验逻辑复用预览接口：前端传入 bodyText + knowledgeContent + skillContent + overallRules + resumeId 调 AI。后端分别调用 `parseDimensionMarkdown` 解析两维度，再动态生成 schema 逐项验证 answer（boolean）和 evidence（string|null）。预览校验超时时间 30 秒。

### 6.3 问题文本（前端展示用）

| 方法 | 路径                                 | 说明                                                                  |
| ---- | ------------------------------------ | --------------------------------------------------------------------- |
| GET  | `/api/prompts/questions?positionId=` | 获取指定职位的当前生效问题文本列表，返回 `[{ key, text, direction }]` |

**知识/技能维度编辑器**：两个独立的 Markdown 文本编辑区域。HR 按 2.1 节语法编写评分规则+方向+问题。编辑器顶部有语法提示条：`### 评分规则`（保留名）→ 方向名 → `1.1 问题` → `评判标准：xxx`。支持复制粘贴批量修改。保存时系统自动解析并校验结构（每维度≥1 个非评分规则方向、每方向≥1 题）。初始内容为从硬编码迁移的 31 题按维度拆分的 Markdown 文本。

**通用评分规则编辑器**：独立 Markdown 文本编辑区域，HR 自由编写综合评分规则文本。初始内容为系统默认评分规则。

**脏状态保护**：HR 在某职位的编辑器中修改了内容但未保存时，切换到其他职位前弹窗提示"当前有未保存的修改，是否放弃？"。放弃则丢弃修改并切换，取消则留在当前编辑器。

## 八、保存与校验流程

```
HR 编辑 bodyText + knowledgeContent + skillContent + overallRules
    │
    ▼
点击 [保存为新版本]
    │
    ▼
填写修改说明（可选）
    │
    ▼
静态校验（前端 + 后端）
  · bodyText 非空 + 含 {{resumeText}}
  · overallRules 非空
  · knowledgeContent 非空，可解析为合法结构（≥1方向、每方向≥1题）
  · skillContent 非空，可解析为合法结构（≥1方向、每方向≥1题）
    │
    ✗ → 拦截，前端提示
    ✓
    ▼
弹窗：选择一份系统简历作为校验样本
    │
    ▼
调 AI 校验（POST /api/prompts/preview）
  · 用当前编辑的四个内容区 + 选中简历 → AI
  · 解析返回 JSON
    │
    ✗ → 报错，列出缺漏项/类型不符项，不写入
    ✓
    ▼
事务写入：
  · 查询当前生效行：`WHERE positionId = X AND isCurrent = true`
  · 有则 UPDATE 旧行 SET isCurrent = false，INSERT 新行（version = 旧行.version + 1, isCurrent = true）
  · 无则 INSERT 新行（version = 1, isCurrent = true）
    │
    ▼
保存成功，提示"已保存为 vN"
```

## 十、初始化迁移

### 10.1 脚本：`scripts/init-prompt-config.ts`

部署前手动执行一次：

```bash
./dev.sh npx tsx scripts/init-prompt-config.ts
```

脚本逻辑：

1. 从 `lib/prompts/screening.ts` 提取 `SCREENING_SYSTEM_PROMPT` → bodyText 基础段落
2. 从 `lib/prompts/screening.ts` 的 `buildScreeningUserPrompt` 提取静态文本，插入 `{{positionTitle}}` 等占位符
3. 将内置的 8 方向 × 31 题数据按维度拆分为两份 Markdown 文本，分别写入 knowledgeContent（knowledge 4 方向）和 skillContent（skill 4 方向），每维度含 `### 评分规则` 段落。完整内容见 M0 初始化脚本
4. 内置 `overallRules` 默认内容（从现有 scorer 规则翻译为自然语言，详见下方）
5. 遍历现有 Position 表，为每个职位 INSERT 一行 `PromptRecord`（`positionId = <职位ID>`，`version = 1`，`isCurrent = true`，changeNote = "从代码迁移初始版本"）

### overallRules 初始默认内容

```markdown
## 通用评分规则

1. 初筛总分 = 知识维度得分 × {{knowledgeWeight}}% + 技能维度得分 × {{skillWeight}}%
2. 知识维度低于 2 星时，综合评分上限为 3 星
3. 任一维度为 1 星时，综合评分直接为 1 星
4. 两个维度的评分规则已分别在各维度的"### 评分规则"中定义，AI 需逐维度执行各自的规则，再按照此处的通用规则综合计算最终星级
```

> 知识维度和技能维度的专属评分规则已分别内嵌在 `knowledgeContent` 和 `skillContent` 字段的 `### 评分规则` 段落中（见 2.1 节 Markdown 语法）。

> **维护约束**：评分规则（knowledgeContent/skillContent 中的 `### 评分规则` 和 overallRules）的所有内容均为 AI 直接执行的指令，必须使用 AI 能够无歧义理解的完整句子描述，避免使用"多数决"等需要专业背景知识的术语。后续修改规则时应保持这一写作标准。

### 10.2 容错

`ai-screener.ts` 启动时不强依赖数据库。评估时若某职位无 PromptRecord，评估直接报错（简历标为 ERROR），不走硬编码 fallback 路径。初始化脚本是唯一的数据来源。

### 10.3 向后兼容

**历史评估数据**：M0 之前的评估结果以旧格式（平铺 Q1-Q31）保存在 `EvaluationDimension.aiDetail` 中。部署后：

- 历史数据**只读展示**，aiDetail JSON 旧格式由前端适配渲染
- 新的评估使用新格式（knowledge/skill 含 directions 数组 + overall 对象），写入同一字段
- `PositionEvaluation` 表结构不变，`EvaluationDimension` 仍只存 knowledge 和 skill 两行（方向级评分通过 aiDetail 携带）

## 十一、风险与注意事项

| 风险                          | 影响                                                                               | 缓解措施                                                                                                                           |
| ----------------------------- | ---------------------------------------------------------------------------------- | ---------------------------------------------------------------------------------------------------------------------------------- |
| SQLite 事务失败               | `isCurrent` 可能出现 0 条或多条生效行，评估时读到错误提示词                        | 保存和回滚全部用 Prisma 交互式事务包裹；启动时自检：每个职位有且仅有一条 `isCurrent = true`，异常时自动修复（取 version 最大的行） |
| 预览校验每次调 AI             | HR 频繁保存时产生 API 费用和等待时间                                               | 预览超时 30 秒，超时提示 HR 重试                                                                                                   |
| AI 打分一致性                 | 同一份简历用同一套提示词评分两次，AI 可能给出不同星级（LLM 概率性输出）            | 评分规则要求 AI 按照自然语言描述严格执行；前端展示评分时可附加置信度说明；temperature=0.3 降低随机性                               |
| 单表 isCurrent 无数据库强约束 | SQLite 不支持 partial unique index，应用层 bug 可能导致同一职位多个 isCurrent=true | 所有写入路径走统一的服务函数，不裸写 SQL；启动时自检修复                                                                           |
| overallRules 被删或写错       | AI 没有评分依据，返回的星级可能随机或缺失                                          | 保存时静态校验 overallRules 非空；schema 校验捕获缺失的 star 字段                                                                  |
