# 简历任务批次管理功能说明

## Context

当前系统中，简历处理任务（邮件获取、解析、筛选）缺乏统一的任务追踪机制。用户无法直观了解任务执行进度、统计数据和异常情况。本功能模块构建了一套完整的批次管理系统，支持：

1. **任务追踪** — 每次操作创建批次记录，实时追踪处理进度
2. **分类管理** — 按任务类型（获取/解析/筛选）分类显示，标签区分
3. **进度可视化** — 进度条 + 统计卡片，实时展示处理状态
4. **操作控制** — 支持停止进行中的任务、删除已完成的任务
5. **异常处理** — 区分解析异常和筛选异常，提供详细的错误信息

## 二、数据库设计

### 2.1 TaskBatch 模型

```prisma
model TaskBatch {
  id               String       @id @default(cuid())
  batchNo          String       @unique  // 批次编号，如 "20260608-001"
  source           String       // 来源类型: "scheduled" | "manual" | "rescreen" | "parse"
  sourceDetail     String?      // 来源详情，如 "定时任务"、"批量AI筛选"
  emailConfigId    String?      // 关联的邮箱配置（仅获取任务）

  totalResumes     Int          @default(0)  // 总简历数
  parsedCount      Int          @default(0)  // 已解析数
  screenedCount    Int          @default(0)  // 已筛选数
  errorCount       Int          @default(0)  // 解析异常数
  screenErrorCount Int          @default(0)  // 筛选异常数

  status           String       @default("processing")  // "processing" | "completed"
  startedAt        DateTime     @default(now())
  completedAt      DateTime?

  resumes          Resume[]     @relation("BatchResumes")           // 获取批次关联的简历
  screeningResumes Resume[]     @relation("ScreeningBatchResumes")  // 筛选批次关联的简历

  createdAt        DateTime     @default(now())
  updatedAt        DateTime     @updatedAt
}
```

### 2.2 Resume 模型新增字段

```prisma
model Resume {
  // ... 现有字段 ...

  screeningBatchId String?      // 关联的筛选批次
```

### 2.3 批次编号生成规则

```
格式: YYYYMMDD-NNN
示例: 20260608-001, 20260608-002

生成逻辑:
1. 查询当天最大的批次编号
2. 提取序号部分并 +1
3. 如果当天无批次，序号从 001 开始
```

### 3.2 批次创建流程

```
createBatch(input)
│
├─ 1. 生成批次编号 (YYYYMMDD-NNN)
│
├─ 2. 创建 TaskBatch 记录
│   ├─ source = input.source
│   ├─ sourceDetail = input.sourceDetail
│   ├─ totalResumes = input.resumeIds.length
│   └─ status = "processing"
│
├─ 3. 关联简历
│   ├─ 获取批次 (scheduled/manual): 设置 resume.batchId
│   ├─ 解析批次 (parse): 设置 resume.batchId（在 API 中处理）
│   └─ 筛选批次 (rescreen): 设置 resume.screeningBatchId（在 API 中处理）
│
└─ 4. 返回批次信息
```

### 3.3 进度更新逻辑

```typescript
// updateBatchProgress 核心逻辑
async function updateBatchProgress(batchId: string) {
  // 1. 查询批次信息
  const batch = await prisma.taskBatch.findUnique({ where: { id: batchId } })

  // 2. 根据批次类型查询关联简历
  let resumes
  if (batch.source === 'rescreen') {
    // 筛选批次：通过 screeningBatchId 查询
    resumes = await prisma.resume.findMany({
      where: { screeningBatchId: batchId }
    })
  } else {
    // 其他批次：通过 batchId 查询
    resumes = await prisma.resume.findMany({
      where: { batchId: batchId }
    })
  }

  // 3. 统计各状态数量
  const parsingCount = resumes.filter(r => r.status === 'PARSING').length
  const screeningCount = resumes.filter(r => r.status === 'SCREENING').length
  const passedCount = resumes.filter(r => r.status === 'PASSED').length
  const failedCount = resumes.filter(r => r.status === 'FAILED').length
  const errorResumeIds = resumes.filter(r => r.status === 'ERROR').map(r => r.id)

  // 4. 根据批次类型区分异常类型
  if (batch.source === 'parse') {
    // 解析批次：所有 ERROR 都算解析异常
    parseErrorCount = errorResumeIds.length
    screenErrorCount = 0
  } else if (batch.source === 'rescreen') {
    // 筛选批次：所有 ERROR 都算筛选异常
    parseErrorCount = 0
    screenErrorCount = errorResumeIds.length
  } else {
    // 获取批次：根据是否有筛选记录区分
    parseErrorCount = ERROR且无筛选记录的数量
    screenErrorCount = ERROR且有筛选记录的数量
  }

  // 5. 计算进度
  parsedCount = PARSED + PENDING + SCREENING + PASSED + FAILED 的数量
  screenedCount = PASSED + FAILED 的数量

  // 6. 判断批次状态
  hasProcessing = parsingCount > 0 || screeningCount > 0
  newStatus = hasProcessing ? 'processing' : 'completed'

  // 7. 更新批次记录
  await prisma.taskBatch.update({
    where: { id: batchId },
    data: {
      totalResumes,
      parsedCount,
      screenedCount,
      errorCount: parseErrorCount,
      screenErrorCount,
      status: newStatus,
      completedAt: newStatus === 'completed' ? new Date() : null
    }
  })

  // 8. 批次完成时，清除筛选批次的 screeningBatchId
  if (batch.source === 'rescreen' && newStatus === 'completed') {
    await prisma.resume.updateMany({
      where: { screeningBatchId: batchId },
      data: { screeningBatchId: null }
    })
  }
}
```

### 3.4 停止批次逻辑

```typescript
// stopBatch 核心逻辑
async function stopBatch(batchId: string) {
  // 1. 验证批次状态
  const batch = await prisma.taskBatch.findUnique({ where: { id: batchId } })
  if (batch.status !== 'processing') {
    throw new Error('批次已完成，无法停止')
  }

  // 2. 根据批次类型重置简历状态
  if (batch.source === 'rescreen') {
    // 筛选批次：SCREENING → PENDING，清除 screeningBatchId
    await prisma.resume.updateMany({
      where: { screeningBatchId: batchId, status: 'SCREENING' },
      data: { status: 'PENDING', screeningBatchId: null }
    })
  } else {
    // 获取/解析批次：PARSING → UNPARSED
    await prisma.resume.updateMany({
      where: { batchId: batchId, status: 'PARSING' },
      data: { status: 'UNPARSED' }
    })
  }

  // 3. 更新批次状态为已完成
  await prisma.taskBatch.update({
    where: { id: batchId },
    data: { status: 'completed', completedAt: new Date() }
  })
}
```

### 5.2 批次卡片组件

每个批次卡片显示以下信息：

**第一行：基本信息**
- 批次编号（如 `#20260608-001`）
- 任务类型标签（获取任务/解析任务/筛选任务）
- 状态标签（进行中/已完成）
- 来源描述（如"定时任务"、"批量AI筛选"）

**第二行：进度条**
- 获取任务：解析进度 + 筛选进度
- 解析任务：仅解析进度
- 筛选任务：仅筛选进度

**第三行：状态信息**
- 创建时间
- 处理中的数量
- 异常数量

**右侧操作按钮**
- 停止按钮：仅"进行中"批次显示（橙色圆形图标）
- 删除按钮：仅"已完成"批次显示（红色垃圾桶图标）
- 展开/收起按钮

```
│                                        │                        │
│                                        ▼                        │
│   ┌──────────┐    ┌──────────┐    ┌──────────┐                 │
│   │  完成     │◄───│ 更新状态  │◄───│ AI 筛选   │                 │
│   └──────────┘    └──────────┘    └──────────┘                 │
│                                                                 │
│   状态流转: PENDING/PASSED/FAILED → SCREENING                   │
│            → PASSED（通过）或 FAILED（未通过）或 ERROR（异常）   │
│                                                                 │
└─────────────────────────────────────────────────────────────────┘
```

## 七、异常处理

### 7.1 异常类型分类

| 异常类型 | 触发条件 | 统计字段 | 显示位置 |
|---------|---------|---------|---------|
| 解析异常 | 文件不存在、文本质量不合格、解析过程错误 | errorCount | 解析失败 |
| 筛选异常 | AI API 调用失败、返回结果无效、筛选过程错误 | screenErrorCount | 筛选异常 |

### 7.2 异常统计规则

```typescript
// 根据批次类型区分异常统计
if (batch.source === 'parse') {
  // 解析批次：所有 ERROR 都算解析异常
  parseErrorCount = errorResumeIds.length
  screenErrorCount = 0
} else if (batch.source === 'rescreen') {
  // 筛选批次：所有 ERROR 都算筛选异常
  parseErrorCount = 0
  screenErrorCount = errorResumeIds.length
} else {
  // 获取批次：根据是否有筛选记录区分
  parseErrorCount = ERROR且无筛选记录的数量
  screenErrorCount = ERROR且有筛选记录的数量
}
```

### 7.3 常见异常信息

**解析异常**:
- "文本质量不合格（得分 82，阈值 40），疑似乱码或不可解析的内容"
- "文本内容过短（35 字符，最低要求 50 字符），可能为无效解析结果"
- "简历文件不存在，无法重新解析"

**筛选异常**:
- "AI筛选失败: 402 Insufficient Balance"
- "AI筛选结果无效：评分为 0，可能是简历文件格式错误或内容无法识别"

### 7.4 停止批次的状态重置

| 批次类型 | 重置规则 |
|---------|---------|
| 获取批次 | PARSING → UNPARSED |
| 解析批次 | PARSING → UNPARSED |
| 筛选批次 | SCREENING → PENDING，清除 screeningBatchId |

## 十、验证方案

1. **构建验证:** `yarn build` 确保无类型错误
2. **Schema 迁移:** `npx prisma generate && npx prisma db push` 验证迁移成功

7. **删除功能测试:** 对"已完成"批次点击删除，验证批次记录删除
8. **异常统计测试:** 触发解析/筛选异常，验证 errorCount 和 screenErrorCount 正确
9. **自动刷新测试:** 观察页面每 3 秒自动刷新，切换标签页立即刷新
