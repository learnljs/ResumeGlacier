# 简历复用评估 — 开发方案

> **优先级**：P0（核心功能，涉及数据模型重构）
>
> **目标**：实现简历复用评估功能，让一份简历可对多个岗位产生独立评估结果，HR 可从已有简历库中为任意岗位重新检索、评估并主动联系潜在匹配候选人。
>
> **状态**：规划阶段，尚未开始实施

---

## 一、需求分析

### 1.1 核心问题

当前系统中 Resume、Position、ScreeningResult 三者耦合过紧：

- 一份简历只能产生一条 AI 评估结果（`Resume` 1:1 `ScreeningResult`，`resumeId` 上有 `@unique` 约束）
- 跟进记录（`FollowUpRecord`）直接绑定简历（`resumeId @unique`），而非某次具体评估
- 评估条件不存在结构化存储

### 1.2 改造目标

将评估结果从简历中解耦，建立独立的 `PositionEvaluation` 模型，实现：

```
Resume ──1:N── PositionEvaluation ──1:1── FollowUpRecord
                  │
               Position
```

### 1.3 功能模块划分

| 模块 | 说明 |
|------|------|
| **M1. 数据模型改造** | 新建 PositionEvaluation，改造 FollowUpRecord，简化 Resume 状态机，删除 ScreeningResult |
| **M2. 复用评估页面** | 新建页面：岗位选择 + 评估条件 + 候选人列表 + 发起 AI 评估 |
| **M3. 已筛选页面改造** | 列表粒度从 Resume 改为 PositionEvaluation，状态筛选改得分范围筛选 |
| **M4. 跟进管理改造** | FollowUpRecord 绑定 PositionEvaluation，数据源适配 |
| **M5. 队列改造** | 评估队列支持两种任务类型：正常评估（initial）+ 复用评估（reevaluate） |
| **M6. 数据迁移** | ScreeningResult → PositionEvaluation，Resume 字段清理，状态值迁移 |

#### 2.1.2 新建 PositionEvaluation 模型

```prisma
model PositionEvaluation {
  id             String   @id @default(cuid())
  resumeId       String
  positionId     String
  aiConfigId     String?
  summary        String                       // AI 评估摘要
  strengths      String                       // AI 评估优势
  weaknesses     String                       // AI 评估劣势
  aiTags         String?                      // JSON: AI 标签数组
  aiModel        String                       // AI 模型名称
  tokenUsage     Int?                         // Token 消耗
  processingTime Int?                         // 处理耗时(ms)
  initialScore   Float?                       // 初筛得分（0-100）
  compositeScore Float?                       // 综合得分（0-100）
  conditions     String?                      // JSON: 评估条件快照
  screenedAt     DateTime?                    // 评估时间
  screeningBatchId String?                    // 筛选批次
  createdAt      DateTime  @default(now())

  resume          Resume          @relation(fields: [resumeId], references: [id], onDelete: Cascade)
  position        Position        @relation(fields: [positionId], references: [id])
  aiConfig        AIConfig?       @relation(fields: [aiConfigId], references: [id])
  screeningBatch  TaskBatch?      @relation("ScreeningBatchEvaluations", fields: [screeningBatchId], references: [id])
  followUpRecord  FollowUpRecord?
  evaluationDimensions EvaluationDimension[]

  @@unique([resumeId, positionId])
}
```

> 与 `ScreeningResult` 的差异：新增 `positionId`（多岗位支持）、`initialScore`/`compositeScore`（从 Resume 迁移）、`conditions`（评估条件快照）、`screenedAt`（从 Resume 迁移）。去掉了 `resumeId` 的 `@unique`，改为 `@@unique([resumeId, positionId])`（复合唯一）。

#### 2.1.3 改造 FollowUpRecord 模型

变更点：
- 新增 `evaluationId String` 字段（关联 PositionEvaluation）
- 新增 `updatedAt DateTime @updatedAt` 字段（当前缺失）
- 移除 `resumeId` 上的 `@unique` 约束
- 新增 `@@unique([evaluationId])` 约束（一个评估最多一条跟进）
- **保留** `resumeId`：跟进管理页面列表中需要候选人姓名等简历维度信息，保留直接关联可避免额外 JOIN

```prisma
model FollowUpRecord {
  id            String    @id @default(cuid())
  evaluationId  String
  resumeId      String                     // 保留：便于直接查询简历维度数据
  note          String?
  status        String    @default("CONTACTING")
  interviewTime String?
  salaryRange   String?
  startDate     String?
  jobLevel      String?
  rejectReason  String?
  createdAt     DateTime  @default(now())
  updatedAt     DateTime  @updatedAt       // ← 新增

  evaluation PositionEvaluation @relation(fields: [evaluationId], references: [id], onDelete: Cascade)
  resume     Resume             @relation(fields: [resumeId], references: [id], onDelete: Cascade)
  tags       FollowUpRecordTag[]
  logs       FollowUpLog[]

  @@unique([evaluationId])
}
```

#### 2.1.4 Resume 状态机简化

**当前实际使用的状态值**：

| 状态 | 设置位置 | 说明 |
|------|----------|------|
| `UNASSIGNED` | 手动/未匹配时 | 未分配岗位 |
| `UNPARSED` | email-fetcher.ts | 待解析 |
| `PARSING` | parsing queue | 解析中 |
| `PARSED` | parsing-worker-processor.ts | 已解析（无 position 匹配时） |
| `PENDING` | parsing-worker-processor.ts | 待筛选（有 position 匹配时） |
| `SCREENING` | screening-queue.ts | AI 筛选中 |
| `PASSED` | ai-screener.ts | AI 评估通过 |
| `FAILED` | —（已弃用） | AI 评估未通过 |
| `ERROR` | 各队列 catch 块 | 异常 |

**移除字段**（迁移到 PositionEvaluation）：
- `initialScore`、`compositeScore`、`screenedAt`、`screeningBatchId`

**状态枚举变更**：

```
旧: UNPARSED → PARSING → PARSED → PENDING → SCREENING → PASSED/FAILED
                                                           ↑ 删除

新: UNPARSED → PARSING → PENDING → SCREENING → SCREENED
                ↑ 删除 PARSED（与 PENDING 合并，按是否有 positionId 区分）
```

| 状态 | 说明 |
|------|------|
| `UNASSIGNED` | 未分配岗位（保留） |
| `UNPARSED` | 待解析 |
| `PARSING` | 解析中 |
| `PENDING` | 待筛选（原 PARSED 合并至此，有 positionId 才可进入 SCREENING） |
| `SCREENING` | 筛选中 |
| `SCREENED` | 已评估（替代 PASSED/FAILED，具体结果看 PositionEvaluation） |
| `ERROR` | 异常 |

#### 2.1.5 删除旧 ScreeningResult 模型

数据迁移完成后删除。其字段由 PositionEvaluation 承接，关联关系（AIConfig）保留。

同时 `AIConfig` 模型中的 `screeningResults ScreeningResult[]` 关系需改为指向 `PositionEvaluation`。

#### 2.1.6 EvaluationDimension 适配

当前 `EvaluationDimension` 已有 `positionId` 字段，迁移方案有两种：

**方案 A（推荐）**：`resumeId` 改为关联 `PositionEvaluation`
- 优点：评估维度直接绑定评估记录，语义清晰
- 需改：`resumeId` → `evaluationId`，关联改为 `PositionEvaluation`

**方案 B**：保持不变，通过 `(resumeId, positionId)` 复合查询
- 优点：无需迁移 EvaluationDimension 数据
- 缺点：与 `FollowUpRecord` 的设计不一致

> 本方案采用 **方案 A**，与 FollowUpRecord 的 `evaluationId` 模式保持一致。

### 2.2 业务规则

| # | 规则 | 实现方式 |
|---|------|----------|
| 1 | 同一简历+岗位唯一 | `@@unique([resumeId, positionId])`，每次评估 upsert 覆盖旧记录 |
| 2 | 一份简历可评多个岗位 | 各自独立存储，互不影响 |
| 3 | 跟进状态全局排除 | 对任意岗位有非 `UNSUITABLE` 跟进记录的简历不进入复用池 |
| 4 | 部门默认筛选 | Resume.positionId → Position.department，仅同部门简历进入候选池 |
| 5 | 评估条件不存岗位 | 仅存于 PositionEvaluation.conditions JSON 快照 |
| 6 | 硬性条件应用层过滤 | 解析 structuredData JSON 逐条比对 |
| 7 | 使用目标岗位初筛模型 | 岗位无默认模型时前端按钮置灰 |
| 8 | 跟进绑定评估结果 | FollowUpRecord.evaluationId，一个评估最多一条跟进 |
| 9 | UNASSIGNED 简历不进候选池 | 无岗位无法做部门匹配，直接排除 |
| 10 | structuredData 为空不进候选池 | 数据不完整，直接排除 |

### 2.3 评估条件快照结构

```json
{
  "positionId": "xxx",
  "minEducation": "本科",
  "schoolTier": "985/211",
  "majors": "计算机科学,软件工程",
  "minWorkYears": 3,
  "englishLevel": "六级"
}
```

所有字段可选，`null` 或不传表示该维度不限制。

### 2.4 候选池生成逻辑

```
输入：positionId + conditions
步骤：
  1. 查询目标岗位的 department
  2. 查询同部门所有已解析简历（排除 UNASSIGNED）
  3. 从 PositionEvaluation + FollowUpRecord 找出「跟进中」的 resumeId 集合
  4. 排除跟进中的简历（UNSUITABLE 不排除）
  5. 应用层解析 structuredData JSON，逐条比对 5 项硬性条件
  6. 查询目标岗位的历史评估数据（知识/技能星级、初筛得分）
  7. 返回候选列表
```

**候选池过滤 SQL 伪代码**：

```sql
SELECT r.*
FROM Resume r
JOIN Position p ON r.positionId = p.id
WHERE p.department = (SELECT department FROM Position WHERE id = :targetPositionId)
  AND r.status IN ('PENDING', 'SCREENING', 'SCREENED')
  AND r.positionId IS NOT NULL          -- 排除 UNASSIGNED
  AND r.structuredData IS NOT NULL      -- 排除无结构化数据的简历
  AND r.id NOT IN (
    -- 排除任意岗位跟进中（非 UNSUITABLE）的简历
    SELECT DISTINCT pe.resumeId
    FROM PositionEvaluation pe
    JOIN FollowUpRecord fr ON fr.evaluationId = pe.id
    WHERE fr.status <> 'UNSUITABLE'
  )
```

### 2.5 已筛选 vs 跟进管理的数据分界线

```
已筛选列表 = 有 PositionEvaluation 且（无 FollowUpRecord 或 FollowUpRecord.status = UNSUITABLE）
跟进管理   = 有 PositionEvaluation 且有 FollowUpRecord（status ≠ UNSUITABLE）
```

取消跟进（删除 FollowUpRecord）→ PositionEvaluation 保留 → 候选人回到已筛选列表。

## 五、队列改造

### 5.1 当前状态

**ScreeningQueue.QueueItem**（`lib/services/screening-queue.ts:12-16`）：

```typescript
interface QueueItem {
  resumeId: string
  aiConfigId?: string
  positionId?: string
}
```

- 无 `type` 字段区分任务类型
- Worker 统一调用 `screenResume()`，始终写入 `ScreeningResult` 并设置 `status = 'PASSED'`

**解析队列 Worker**（`lib/services/parsing-worker-processor.ts:104`）：

```typescript

status: positionMatch ? 'PENDING' : 'PARSED'
// → 改造后统一为 'PENDING'，有 positionId 的才可入队
```

### 5.2 任务类型区分

队列任务增加 `type` 字段：

```typescript
// 正常首次评估（新收简历自动触发）
type InitialTask = {
  type: 'initial'
  resumeId: string
}

// 复用评估（从复用评估页面手动触发）
type ReevaluateTask = {
  type: 'reevaluate'
  resumeId: string
  positionId: string
  conditions: Record<string, unknown>
  batchId?: string
}

type QueueItem = InitialTask | ReevaluateTask
```

### 5.3 Worker 处理分支

```
if type === 'initial':
  positionId = Resume.positionId
  使用 positionId 对应岗位的默认初筛模型（Position.defaultInitialModelId）
  → 写入 PositionEvaluation（create）
  → 更新 Resume.status = SCREENED

if type === 'reevaluate':
  positionId = task.positionId
  使用目标岗位的默认初筛模型
  → 写入 PositionEvaluation（upsert，同 resumeId+positionId 覆盖旧记录）
  → 不改变 Resume.status
```

### 5.4 TaskBatch.source 新增值

```prisma
// TaskBatch.source 新增值: "reevaluate"
// 完整枚举: "scheduled" | "manual" | "rescreen" | "reevaluate"
```

进度统计逻辑：
- 总数 = 入队任务数
- 完成数 = 已评估数（PositionEvaluation 创建/更新成功）
- 错误数 = 评估失败数

## 六、数据迁移方案

### 6.1 迁移脚本

**脚本路径**：`scripts/migrate-to-position-evaluation.ts`

**前置条件**：

1. 先执行 `prisma db push` 创建 PositionEvaluation 表、修改 FollowUpRecord、修改 Resume
2. 备份 `prisma/data/resume.db`
3. 建议设置 `PARSING_CONCURRENCY=0`、`SCREENING_CONCURRENCY=0` 避免队列干扰

**迁移步骤**：

```
1. 创建 PositionEvaluation 记录：
   遍历所有 ScreeningResult：
     a. 通过 resumeId 获取 Resume.positionId
     b. 若 positionId 为空，跳过
     c. 在 PositionEvaluation 创建记录：
        - resumeId, positionId
        - 复制 summary, strengths, weaknesses, aiTags, aiModel,
          tokenUsage, processingTime, aiConfigId, createdAt
        - initialScore = Resume.initialScore
        - compositeScore = Resume.compositeScore
        - screenedAt = Resume.screenedAt
        - screeningBatchId = Resume.screeningBatchId

2. 迁移 EvaluationDimension：
   遍历所有 EvaluationDimension：
     a. 通过 (resumeId, positionId) 找到对应的 PositionEvaluation
     b. 将 resumeId 改为 evaluationId（关联 PositionEvaluation）

3. 更新 FollowUpRecord：
   遍历所有 FollowUpRecord：
     a. 通过 resumeId → Resume.positionId 找到对应的 PositionEvaluation
     b. 设置 evaluationId
     c. 移除 resumeId 的 @unique 约束

4. 更新 Resume 状态：
   a. PASSED/FAILED → SCREENED
   b. PARSED → PENDING

5. 验证数据完整性：
   a. ScreeningResult 数量 = PositionEvaluation 数量
   b. FollowUpRecord 数量不变，全部已关联 evaluationId
   c. 各分数总和一致：迁移前后 SUM(initialScore) 相等

6. 删除旧模型和字段：
   a. 删除 ScreeningResult 表
   b. 删除 Resume.initialScore, compositeScore, screenedAt, screeningBatchId
   c. 清理 AIConfig.screeningResults 关系
```

### 6.2 回滚方案

迁移前备份 `prisma/data/resume.db`，验证失败时恢复备份 + 重新 `prisma db push` 恢复旧 schema。

## 九、风险与注意事项

### 9.1 数据安全

- 迁移脚本执行前**必须**备份 `prisma/data/resume.db`
- 迁移后验证数据完整性，确认无误后再删除旧模型
- 建议在非生产环境先跑一遍完整流程
- **切勿在迁移过程中让队列运行**（设置并发为 0）

### 9.2 SQLite 限制

- Prisma `db push` 对 SQLite 的 ALTER TABLE 支持有限，复杂变更走「重建表→导数据→删旧表」流程
- SQLite 不支持并发写，迁移脚本应单线程执行
- 大表（如 EvaluationDimension）的 `resumeId → evaluationId` 迁移是全表扫描，可能较慢

### 9.3 性能考量

- 候选池应用层过滤在 ≤2000 条级别性能可接受
- 若候选池量级持续增长，可考虑将常用硬性条件字段（学历、工作年限）提取为独立列，建索引
- 部门匹配依赖 `Position.department`，建议确保该字段有合理填充率

### 9.4 API 兼容性

- `GET /api/evaluations` 改造后，原有的 `?resumeId=&positionId=` 参数仍保留支持（重命名为单条查询模式），确保详情页评估维度加载不受影响
- `POST /api/follow-up/records` 的 body 变更（`resumeId` → `evaluationId`）是 breaking change，需与前端同步上线
- 建议所有 API 改造采用 `v2` 路径或通过请求参数区分新旧逻辑，给前端切换留缓冲期

### 9.5 回滚考量

- 迁移前的完整数据库备份是唯一可靠的回滚手段
- schema 变更不可逆（删除 ScreeningResult 表后无法简单恢复）
- 建议在迁移后保留备份至少 7 天
