# PDF 简历头像提取 - 视觉确认优化方案

> **任务背景**：基于 [PDF简历头像提取优化-开发方案.md](./PDF简历头像提取优化-开发方案.md) 完成的 v1 实现（结构分析 + 渲染滑窗 + 肤色/边缘启发式评分）在实际运行中**误检率偏高**——会把 logo、彩色横幅、木纹背景、装饰图等非头像区域当成头像提取出来。本方案针对该问题重构判定逻辑，引入 AI 视觉模型做"是否人脸"的最终确认。
>
> **核心结论**：v1 流水线从头到尾没有任何一步真正确认"这是张脸"，所有验证都是肤色/位置/边缘密度等代理信号，而 logo/木纹/米色背景都容易满足这些代理条件。本方案用 AI 视觉模型替代启发式判定，预期误检率从 ~15% 降至 ≤ 5%。

## 1. 问题诊断

### 1.1 失败模式

实际运行中，**误检为主**（把非头像区域当头像提取），且阶段 1（整张内嵌非人脸图，如 logo/装饰图）与阶段 2（从渲染页面裁出的一块，如彩色页眉/文字段落/背景色块）两种误检都有出现。

### 1.2 误检的直接来源（按影响排序）

| # | 位置 | 问题 |
|---|------|------|
| 1 | `pdf-image-extractor-direct.ts:288-301` | **阶段 1 的"0.6 盲回退"**：所有候选未通过肤色验证时，仍把"页面上方 40% 的第一个候选"以置信度 0.6 返回，**完全不检查是不是脸**。任何位于上方的 logo/装饰图都会被当成头像。 |
| 2 | `app/api/resumes/[id]/photo/route.ts:48-55` | **API 无置信度门禁**：只要 `extractPhotoFromPdf` 返回非 null 就保存，不看 confidence。0.6 盲回退的误检直接落到用户脸上。解析流水线 `resume-parser.ts:608` 同理。 |
| 3 | `pdf-image-extractor-direct.ts` `hasSkinTone` | **灰度/黑白照片永远过不了肤色检测**：YCbCr 肤色区间 Cb∈[77,127]、Cr∈[133,173]，而灰度图 R=G=B 时 Cb=Cr=128，两个都越界。黑白证件照必然走 0.6 盲回退或漏检。 |
| 4 | `pdf-image-extractor-direct.ts:219-228` | **变换矩阵解析忽略 CTM 栈**：只记录最近一个 `OPS.transform`，没有处理 `q`/`Q`（save/restore）的矩阵嵌套与累乘。真实 PDF 里图片常被包在 `q ... cm ... Q` 组里，导致算出的坐标错误，位置过滤（跳过下方 60%、跳过宽 >50% 的大图）误杀真照片或放过错图。 |
| 5 | `pdf-image-extractor.ts` `calculatePhotoScore` | **阶段 2 滑窗评分无脸确认**：全是肤色比例 + 颜色方差 + 边缘密度的启发式，木纹/米色背景/橙色 logo 都能拿到 >0.5 分被裁出来。 |

### 1.3 根因

**系统性缺失"脸确认"环节。** 所有"验证"都是与脸相关的代理信号，没有任何一步真正判断"这是不是一张人脸"。代理信号能缩小范围，但无法做最终判定——这正是误检的根源。

## 2. 方案选型

针对"无脸确认"根因，讨论了四条路线：

| 路线 | 要点 | 取舍 |
|------|------|------|
| **A. AI 视觉为主（选定）** | 视觉模型确认"是否人脸 / 找人脸 bbox"，替代启发式判定 | 准确率最高，能处理黑白/深肤色/遮挡，零原生依赖；需配置视觉模型，每份 1-2 次调用、延迟 1-3s |
| B. 本地人脸检测模型 | BlazeFace / MediaPipe 替代启发式 | 离线免费快，但加依赖体积与 Docker 原生/WASM 绑定负担，小图漏检率高 |
| C. 本地预筛 + 视觉兜底 | 本地模型过滤 + 视觉确认疑似候选 | 准确率与成本平衡，但实现复杂度最高，本地预筛正是当前失败的肤色代理 |
| D. 只修 bug + 收紧启发式 | 修确定性 bug + 收紧阈值，不引入新依赖 | 无新依赖，但无脸确认根因未解，误检降低有天花板 |

**选 A 的理由：**

1. **痛点是误检，要高精确率**——视觉大模型判断"是否人脸"的精确率远高于 BlazeFace（简历内嵌头像常是小图、低清、黑白，BlazeFace 在小图上漏检率高，会把误检治成漏检）。
2. **量小，成本/延迟不是问题**——邮件涓流收取（cron 每 30 分钟），一天几十份 × 1-2 次视觉调用，成本可忽略；解析异步，1-3s 无感；唯一实时路径是"重新提取"按钮，用户本就预期等待。
3. **不加重 Docker 原生依赖负担**——项目已在 canvas / sharp / tesseract.js-core / pdfjs polyfill 上吃了苦头，A 只用现成 OpenAI SDK 多发一次 HTTP，零原生依赖。
4. **能治启发式/本地模型治不了的硬骨头**——黑白照、深肤色、卡通/插画头像、强阴影遮挡，视觉模型都能处理。
5. **代码更少**——可删掉整个阶段 2 滑窗评分与肤色验证，净减代码。

**不选 C 的理由**：C 的本地预筛正是当前失败的肤色代理；预筛要真有用就得是完整人脸检测器（≈ B 的复杂度），等于同时维护本地模型 + 视觉两条路。它只在高 volume、要省 API 钱时才划算，本项目不是。

D 的确定性 bug 修复（CTM 栈、置信度门禁）有价值，**并入 A 一起做**。

## 3. 整体架构与级联流程

### 3.1 流程对比

**v1 流程：**

```
extractPhotoFromPdf
  ├─ 阶段1 extractPhotoByStructure  -> 结构分析 + 肤色验证 + 0.6盲回退（自己拍板）
  └─ 阶段2 extractPhotoByRendering  -> 渲染整页 + 滑窗评分（自己拍板）
```

**新流程：**

```
extractPhotoFromPdf
  ├─ 阶段1 extractPhotoByStructure（保留 + 修 CTM 栈 + 放宽过滤）
  │     职责收窄：只产出"候选内嵌图列表"（带正确坐标），不再自己决定头像
  │     肤色检测降级为候选排序的弱信号，不作为采纳依据
  │
  ├─ 场景A verifyCandidatesByVision（候选列表）         <- 模板 PDF 路径
  │     一次视觉调用批量确认：哪张是人脸头像 + 置信度
  │     命中 -> 用该候选图本身作为头像（内嵌图本就是照片区域）-> 返回
  │
  ├─ 场景B extractPhotoByRendering（扫描件，阶段1 零候选）
  │     渲染整页 -> 一次视觉调用"找头像 bbox" -> 按 bbox 扩边裁剪 -> 返回
  │     （删除 calculatePhotoScore 滑窗评分 + 尺寸/步长循环）
  │
  └─ 都没命中 -> null
```

### 3.2 关键取舍

1. **阶段 1 不再"拍板"**——删掉 0.6 盲回退和"肤色验证通过即采纳"。它只负责用 PDF 结构信息高效圈出候选（免费且快），把"是不是脸"的判定权交给视觉模型。肤色检测可保留作候选排序弱信号（上方优先、接近证件照尺寸优先），但排序错了也不怕，最终由视觉确认。
2. **阶段 1 命中时，候选图本身就是头像**——内嵌图经尺寸/宽高比过滤后已是"照片大小的图"，视觉确认是人脸后直接用这张图，不再算 bbox 裁剪（简化）。bbox 裁剪只在阶段 2（扫描件，整页里找人）需要。
3. **阶段 2 滑窗评分整段删除**——`calculatePhotoScore`、`findPhotoOnCanvas` 的尺寸×步长四重循环全删，换成"渲染整页 -> 一次视觉调用找 bbox"。既去误检源，又比滑窗快。
4. **0.6 盲回退删除**——没有视觉确认就不返回任何图，宁缺毋滥。
5. **集成点不变**——`extractPhotoFromPdf` 是单一入口，解析流水线（`resume-parser.ts:extractAndSavePhoto`）和按需 API（`/api/resumes/[id]/photo`）都走它，改一处两边生效。DOCX 头像提取仍不在本次范围。

**每份简历最多 1-2 次视觉调用**（模板 PDF 1 次批量确认；扫描件 1-2 次按页找 bbox）。

## 4. AI 配置与视觉调用核心设计

### 4.1 新增 `vision` 用途（一次性配置）

| 改动点 | 内容 |
|--------|------|
| `types/resume.ts:92` | `AIPurpose` 加 `'vision'` |
| `app/resume/system-config/ai/page.tsx:39` | `purposeOptions` 加 `{ value: 'vision', label: '头像识别', description: '用于简历头像提取确认' }`（badge 渲染自动生效） |
| `lib/services/ai-config-helper.ts` | `getAIConfigByPurpose('vision')` 回退链：显式指定 > vision 默认 > vision 首个 active > **回退 extraction**（常视觉 capable，如 gpt-4o）> 回退 screening > 都没有则抛错（**不回退环境变量**，因为 `OPENAI_MODEL` 可能是 DeepSeek 文本模型） |

用户操作：在「AI模型配置」页加一条 vision-capable 模型（如 `gpt-4o-mini`，便宜快），勾选「头像识别」用途。

### 4.2 阶段 1 过滤放宽（关键协同）

现在有视觉确认兜底，阶段 1 的硬过滤应从"替模型做决定"退化为"去明显无关 + 排序"，把判定权交给视觉，**降低漏检**：

| 过滤项 | v1 | 新 | 理由 |
|--------|-----|-----|------|
| 最小尺寸 | 80px | **50px** | 放过小头像 |
| 宽高比 | 0.5-1.5 | **0.4-2.0** | 放过各种裁剪比例 |
| 下方位置 | 跳过 pageY > 60% | **删除硬过滤** | 部分双栏简历照片在中部；位置保留为排序信号 |
| 大图 | 跳过宽 >50% 页面 | 保留（放宽到 **>60%**） | 明显是背景/横幅，且省 token |
| 候选送视觉前 | - | 按（上方优先 + 接近证件照尺寸优先）排序，取 **top 6** | 限制视觉调用 token |

### 4.3 场景 A：候选批量确认（模板 PDF，阶段 1 有候选）

- **输入**：top-6 候选图，各自 base64 data URI 放进一条 message 的 `content` 数组（多个 `image_url`）。
- **prompt**（中文）：
  > 以下是从简历中提取的若干图片。请判断其中哪一张是人物头像照片（正面或侧面的人脸证件照/半身照，不含 logo、图标、装饰图、纯文字、二维码）。仅返回 JSON：找到返回 `{"faceIndex": 索引(从0开始), "confidence": 0到1}`；都没有返回 `{"faceIndex": null}`。
- **解析**：容错提取首个 `{...}`，不依赖 `response_format`（兼容各 OpenAI 兼容端点，部分不支持）。
- **采纳**：`faceIndex != null && confidence >= 0.7` -> 返回候选图[faceIndex]（内嵌图本身即照片区域，直接 resize 到 max 600）；否则 -> **null**。
- **不回落阶段 2**：阶段 1 已穷尽内嵌图，都不是脸说明简历无照片；回落只会多一次视觉调用却几乎无收益。

### 4.4 场景 B：整页找 bbox（扫描件，阶段 1 零候选）

- 渲染前 1-2 页（每页一次调用），scale 1.5、上限 1200×1600、白底。
- **prompt**：
  > 这是一页简历截图，宽 {W} 像素，高 {H} 像素。请找出其中的人物头像照片区域（正面/侧面人脸证件照或半身照，不含 logo/图标）。仅返回 JSON：找到返回 `{"found": true, "bbox": {"x":,"y":,"w":,"h":}}`（坐标为像素绝对值，基于给定宽高）；无返回 `{"found": false}`。
- **校验 bbox**：`0<=x, x+w<=W, 0<=y, y+h<=H, w>=30 && h>=30`；非法 -> 忽略。
- **裁剪**：bbox 中心扩边 **1.3x**（覆盖头发 + 肩），保持原比例，clamp 到页边，resize max 600 -> 返回。
- 命中即停，不渲染第 2 页。

### 4.5 门禁与置信度

- 门禁收敛在 `extractPhotoFromPdf` 内部：**无视觉确认不返回非 null**。
- 场景 A 阈值 0.7；场景 B `found=true` 即采纳。
- API / 解析流水线层不变：非 null 即保存，confidence 透传（已过门禁，不再二次过滤）。

### 4.6 客户端与超时

- 复用 `createOpenAIClient`（统一 timeout 120s、maxRetries 1）。
- 视觉调用单次 timeout **60s**（`Promise.race`），超时按"未确认"处理（场景 A -> null，场景 B -> 试下页或 null）。

## 5. 错误处理、回退与顺带 bug 修复

### 5.1 视觉调用失败如何处理

区分两种"没结果"：

- **简历无照片**（视觉模型明确说"都不是脸" / `found:false`）-> 返回 null，API 返回 `{ success: false, message: '未检测到照片' }`（沿用现有语义）。
- **视觉服务不可用**（未配置 / 超时 / HTTP 错误 / 模型不支持图片输入）-> **抛错**，API 返回 `{ error: '头像识别服务不可用: …' }`（走现有 catch -> 500），前端 `CandidatePhoto` 已能显示该错误。

| 失败情形 | 处理 | 理由 |
|---------|------|------|
| `vision` 用途未配置 / 无可用模型 | 抛错（提示去配置） | 配置问题要响，不能静默 |
| 调用超时（60s） | maxRetries 已 1 次；仍失败 -> 抛错 | 瞬时故障，按需可重试 |
| 返回非 JSON / 解析失败 | 重试 1 次；仍失败 -> 抛错 | 容错提取首个 `{...}` 后才到这里 |
| 模型不支持图片输入（4xx） | 抛错（透传模型报错） | 配置错误，需用户换视觉模型 |
| 解析流水线中抛错 | `extractAndSavePhoto` 现有 try/catch 吞掉，不阻塞解析 | 简历照常入库，只是没头像，可后续点"重新提取" |

**不保留旧启发式作 fallback。** 视觉不可用 = 没头像（抛错/null），不退回肤色 + 滑窗——那样会把刚消灭的误检又放出来。若日后某部署确实无法用视觉，再单独议。

### 5.2 顺带修复的确定性 bug

| Bug | 修法 | 备注 |
|-----|------|------|
| **CTM 栈被忽略**（`pdf-image-extractor-direct.ts:219`） | 维护 graphics state 栈：`OPS.save` 压栈、`OPS.restore` 出栈、`OPS.transform` 时矩阵相乘累乘 CTM；画图时用累乘后的 CTM 推 pageX/pageY/pageW/pageH。同时把硬编码的 `12/85/86` 换成从 pdfjs 导入的 `OPS.transform` / `OPS.paintImageXObject` / `OPS.paintInlineImageXObject` / `OPS.save` / `OPS.restore` 符号常量 | 坐标准了，位置排序和大图过滤才可靠 |
| **灰度照过不了肤色** | 不单独修——A 方案下肤色检测降为排序弱信号，灰度照由视觉模型识别，自动消解 | - |
| **API 无置信度门禁** | 已在 4.5 收敛：门禁在 `extractPhotoFromPdf` 内，API 层非 null 即保存 | confidence 透传供调试 |
| `page.objs.get` 挂起 | 保留现有 3s `Promise.race` 超时，跳过该候选 | 不变 |
| PDF 结构损坏 / 渲染失败 | 阶段 1 异常 -> 空候选 -> 走场景 B；渲染失败 -> 跳过该页 | 保留现有 try/catch 与 canvas 兼容补丁 |

### 5.3 性能影响

解析流水线每份简历多 1 次视觉调用（模板 PDF，~2s）；扫描件 1-2 次。队列并发仍为 1，但解析本就可能走 Tesseract OCR（30-60s/页），视觉开销相对可忽略。**保持同步**，不做异步解耦（YAGNI）。

## 6. 测试与验证方案

项目无自动化单测、视觉正确性难自动断言，验证以"基准脚本 + 人工批阅"为主。

### 6.1 样本集（ground truth）

从 `data/uploads/` 真实简历策展一份标注集（脱敏），复用 v1 文档 7.2 思路：

| 类型 | 数量 | 标注 |
|------|------|------|
| 模板简历（原生 PDF） | 20 | 有无照片、位置、是否含 logo 干扰 |
| Word 导出 PDF | 15 | 同上 |
| 扫描件 PDF | 10 | 同上 |
| 设计软件 PDF | 5 | 同上 |
| 无照片 PDF | 10 | 确认无照片（测不误检） |

每份标注 `{ id, file, hasPhoto, photoRegion?, pdfType, note }`，存 `data/photo-benchmark/ground-truth.json`，样本放 `data/photo-benchmark/samples/`。**重点覆盖误检诱因**：含 logo/彩色横幅/木纹背景/二维码的简历，以及黑白照、小尺寸照、双栏中部照。

### 6.2 基准脚本

`scripts/photo-extraction-benchmark.ts`，参照 `extraction-benchmark.ts` 模式：

- 遍历样本集，对每份跑 `extractPhotoFromPdf`，记录：命中阶段（A/B）、confidence、耗时。
- 提取的图保存到 `data/photo-benchmark/output/<id>.png`。
- 输出汇总：因"是否正确"需视觉判断，**脚本不自动打分**，而是输出图片 + 元数据表供人工批阅；人工把"对/误检/漏检"填回 `results.json`，脚本再算指标。
- **对比基线**：实现前先用当前（旧）实现跑一遍记录基线，实现后再跑一遍对比（不保留 Legacy 代码，用 git 切旧版跑基线）。

### 6.3 成功指标（为 A 方案调整）

| 指标 | 定义 | 目标 | 旧基线 |
|------|------|------|--------|
| **误检率** | 错误区域被当头像 / 总提取数 | **≤ 5%** | ~15% |
| 准确率 | 正确提取 / 有照片简历数 | ≥ 85% | ~70-75% |
| 漏检率 | 漏掉照片 / 有照片简历数 | ≤ 15% | ~20% |
| 平均耗时 | 总时间 / 份数 | ≤ 2s | 1-3s |

**误检率 ≤ 5% 是硬目标**（本次核心）。耗时目标从 v1 文档的 1s 放宽到 2s，是 A 方案用延迟换准确率的预期代价。

### 6.4 回归 golden set

10 份代表性简历（模板清晰照 / 模板只有 logo 无照 / 扫描件有照 / 扫描件无照 / 黑白照 / 双栏中部照 / 小尺寸照 / 侧脸 / 插画头像 / 部分遮挡照），每次改动后跑这 10 份人工确认无回归（benchmark 脚本加 `--golden` 子集）。

### 6.5 Playwright（轻量）

- 现有 `/resume/test-photo` 错误 UI 测试保留。
- 不为视觉正确性写 Playwright（断言不了"是不是脸"），只做冒烟：导航简历详情 -> 点"重新提取" -> 验证 `<img>` 出现或错误提示出现。
