# 多职位实际同一评价标准 需求文档

## 一、问题背景

公司在不同招聘渠道发布职位时，同一个业务标准职位往往会有多个不同的对外名称（不同平台 JD 命名习惯不同、为获取更多曝光会在同一平台账号下挂多个相似名称的 JD 等）。这些名称虽然对外不同，但实际招聘的是同一类人，使用的招聘要求和评估标准应该是同一套。

与此同时，职位对外名称会随时间变化，历史上使用的职位名称和当前系统中的名称往往对不上。

当前系统按"对外名称 = 独立职位"的方式管理，导致以下业务问题：

### 1. 评估标准分裂

同一个业务标准对外有多个名称时，需要在系统里维护多份内容相同或高度相似的招聘要求和评估标准。HR 修改一次评估标准要同步修改多份，工作量大且容易遗漏出错，无法保证多份标准始终一致。

### 2. 简历无法自动归位

历史简历的邮件主题或附件名使用的是过去的职位曾用名，而当前系统中的职位名已经更新，导致系统无法把这些历史简历匹配到对应的职位上。简历因此积压在异常区，无法进入正常的筛选评估流程。

### 3. 异常简历清理困难

异常区里堆积了大量因为名称不匹配而无法归位的简历。HR 只能逐条手动查看和分配，工作量大、效率低，且无法识别"这些简历都属于同一个曾用名"这种规律。

### 4. 维护成本高

每新增一个对外名称就要新建一个职位，每个职位都要独立维护描述、要求、评估模型，HR 需要为同一个业务标准重复操作多次。

---

## 二、需求目标

1. **统一评估标准**：让业务上的"一个标准职位"对应一套评估标准，无论对外有几个名称，都共用同一套。
2. **解决名称变更的兼容问题**：支持为职位配置多个曾用名 / 同义名，让历史和新进的简历都能自动归位。
3. **降低异常区清理成本**：HR 配置好别名后，异常区里的历史曾用名简历可通过现有批量匹配功能一键归位，无需逐条手动分配。
4. **降低维护成本**：HR 只需要维护一份评估标准，对外多个名称共享。

---

## 三、核心方案

### 1. 引入"职位族"概念

将"业务上的一个标准职位"抽象为"职位族"。一个职位族对应一套评估标准，族下可以有多个具体的对外职位名称（不同平台 / 不同账号下的不同 JD 名称等）。

**关系**：
- 一个职位族 下设 多个职位
- 一个职位 必须归属 一个职位族
- 一个职位族 统一管理初筛的提示词、权重模型（族内所有职位共用同一套评分要求和同一套权重模型）

**业务价值**：
- HR 改一次评估标准，族内所有职位同步生效
- 对外多个名称，但实际是同一标准，管理路径单一
- 删除族条件严苛（族内无关联简历），防止误删历史数据

### 2. 引入"职位别名"机制

允许为每个职位配置多个别名（曾用名、跨平台名称、同义名等），用于在简历归位时识别。

**关键规则**：
- 别名是简历归位的识别字段之一，通过精准匹配识别（与职位主名匹配方式一致）
- 同一职位下别名不能重复
- 别名可随时增删改

**业务价值**：
- 历史曾用名能自动归位，无需人工干预
- 同一平台不同账号下的多个 JD 名称都能识别
- 新加别名后，历史和新进简历都会按新规则归位

### 3. 评估标准按族聚合

职位族的核心职责是**统一管理评估相关的所有配置**（提示词等），确保族内所有职位在筛选时使用同一套评分要求和同一套权重配置，不再存在"族内某个职位的口径与其他职位不一致"的可能。

- 同一族内的职位，**初筛的提示词统一**（保证评分要求一致）
- 同一族内的职位，**初筛的权重模型统一**（保证评分计算口径一致，详见 III.4）
- 冰山模型：与初筛模型同理，**按族统一**，族内所有职位共用同一套冰山模型

### 4. 评估提示词可配置化（详见《提示词维护》文档）

将评估简历用的提示词从代码里抽出来，作为独立的"提示词管理"页面，让 HR 自行维护和调整。HR 在提示词编辑框内可维护一份完整的提示词文本，需要涵盖以下 4 部分：
- 评估角色定位与系统提示词
- 评分维度（知识 / 技能）的思考方向
- 1-5 星各等级的具体判定标准
- 评分步骤与输出格式约束

**入口位置**：系统配置 / 提示词管理

族内所有职位共用同一份提示词，保存后对未来评估立即生效，支持版本管理与一键回滚。

**不在配置范围**（保持代码内置，避免业务配置失误影响整体流程）：
- 简历提取阶段的提示词
- 通用安全约束（如"不带有性别、年龄、学校偏见"等）

## 四、业务规则

### 1. 职位族管理规则

- 职位族是评估标准的管理单元
- 同一族内所有职位共用同一套评估标准
- 删除族：族内**不能有任何关联简历**（很严苛，需先清空所有简历后再删除）
- 停用族：组内**没有还在启用的职位**时才能停用族。族整体不再接受新简历；已存在的简历不受影响
- 启用族：无前置条件，直接启用。族启用不影响族内各职位的独立启停状态（独立维护）

### 2. 职位与族的关系规则

- 新建职位时必须指定归属的职位族（强制入族）
- 职位可随时调整归属族（从 A 族迁到 B 族）
- 调整归属后，简历的评估模型按新族的标准重新计算
- 单独停用 / 启用某个职位，不影响族内其他职位
- **删除职位**：禁止删除有评估结果的职位（与删除族规则一致，严苛保护历史数据）。无评估结果时可删除，删除时主名与所有别名随职位一并清除。简历作为独立业务对象不受影响，简历库中该简历仍然保留，HR 可重新归位到其他职位

### 3. 别名规则

- 别名是手动维护的，由 HR 在职位编辑页维护
- 别名是简历归位的识别字段之一，通过精准匹配识别（与职位主名匹配方式一致）
- 同一职位下别名不能重复
- 别名可随时增删改，修改后对历史和新进简历都生效
- 现有批量匹配职位功能在增强后，会自动识别别名并归位

**别名边界规则**：
- **匹配方式**：精准匹配（与职位主名一致，邮件主题或文件名必须与别名完全相同才命中，不做包含/模糊/关键词匹配）
- **别名数量**：每个职位最多配置 **5 个**别名
- **长度限制**：继承职位名称的长度限制规则
- **字符支持**：与职位名称字符规则保持一致
- **去重规则**：同一职位下别名不能重复
- **全局唯一规则**：所有职位的主名 + 别名，全局不能有任何重复。包括：
  - 同一职位的主名 vs 别名不能重复
  - 任意两个职位之间（不论是否同族）：主名 vs 主名、主名 vs 别名、别名 vs 别名都不能重复
  - 例外：同族内如有特殊业务场景必须重复，**业务上不预留例外**
- **删除职位时**：该职位下所有别名随职位一并清除，不影响其他职位

### 4. 评估模型规则

**重要原则**：职位族是评估相关配置（提示词、权重模型）的**唯一管理单元**，族内所有职位共享同一套配置；权重模型不再挂在单个职位上，而是**只在职位族层级维护**。

- **初筛提示词**：按族绑定，族内所有职位共用同一份
- **初筛权重模型**：按族绑定，族内所有职位共用同一套，记分时按族的权重模型计算
- **冰山模型**：按族绑定，族内所有职位共用同一套，与初筛模型同属族级配置
- **权重模型的管理范围**：权重模型**只属于职位族**，不在职位层维护，职位编辑页不提供权重模型管理入口
- 列表页评分、详情页评分，按候选人投递职位**所属族**配置的权重模型计算（同一族内候选人评分口径完全一致）
- 详情页支持切换同族内的可用模型做横向对比（可选范围限定为该族自身的模型列表）
- 调整族绑定的提示词时，族内所有职位的初筛 AI 调用都使用新版本
- 调整族绑定的权重模型时，族内所有职位的列表 / 详情评分按新模型重新计算
- 职位迁族后，候选人历史评估结果保留在新族下，重新进入初筛时按新族的提示词执行（保留作为历史评估的存档），评分计算也切换到新族的权重模型

- **每个职位族都有统一的一套提示词**：族内所有职位共用同一份提示词进行评分，确保评估一致性
- **每个职位族都有统一的一套权重模型**：族内所有职位共用同一套权重模型进行计分，确保评分计算口径一致；权重模型**只在族级维护**，职位编辑页不提供权重模型管理入口

- **权重模型在族卡片"配置权重模型"入口维护**：点击后打开族的权重模型编辑抽屉/页面，按"初筛模型 / 冰山模型"两个分组维护，族内职位共用
- **提示词可随时调整**：HR 调整提示词后，族内所有职位的初筛 AI 调用使用新版本
- **权重模型可随时调整**：HR 调整族的权重模型后，族内所有职位的列表 / 详情评分按新模型重新计算

- 编辑族（点击"编辑族"按钮，弹出抽屉 / 弹窗编辑族名）
- 停用 / 启用族（族卡片上的"停用族"按钮）
- 删除族（族内不能有任何关联简历）
- 配置提示词（跳转到提示词管理页）
- **配置权重模型**（点击后打开族的权重模型编辑抽屉/页面，按"初筛模型 / 冰山模型"两个分组维护，族内所有职位共用；**这是权重模型管理的唯一入口**）

**职位级操作**（职位行上的按钮）：
- 新建职位（顶部"新建职位"按钮）
- 编辑职位（点击"编辑"打开职位编辑页）
- 停用 / 启用职位（职位行上的"停用"按钮）
- 删除职位（职位行上的"删除"按钮，校验：禁止删除有评估结果的职位）
- 迁移职位到其他族（职位行上的"迁族"按钮）

**其他**：
- **权重模型只属于职位族，不在职位层维护**：职位编辑页**不提供**权重模型管理入口、不展示权重模型相关字段；如需调整权重模型，请到所属族的"配置权重模型"入口
- 保留原有的"已停用职位"入口（页面底部）

- 支持提示词的查看、编辑、版本管理、回滚

**核心元素**：

- **族与卡片 1:1 联动**：在职位管理页新增一个职位族后，提示词管理页**自动同步出现一个对应的编辑卡片**；删除族时同步移除对应卡片（提示词历史保留作为审计存档）；族停用不影响卡片展示，仍可查看但提示"该族已停用"

- **版本历史**：每次保存生成版本，保留最近 30 个，支持查看 / 回滚 / 对比
- **影响范围提示**：保存时提示"族内 N 个职位的初筛 AI 调用将使用新版本"

## 六、验收标准

### 1. 评估标准统一

- 职位族是评估标准（含提示词、权重模型）的管理单元，按族内主职位名称自动生成"X族"
- 同一族内所有职位的初筛提示词完全一致，HR 只维护一份
- 同一族内所有职位的初筛权重模型完全一致，HR 只维护一份
- 同一族内所有职位的冰山模型完全一致，HR 只维护一份
- 修改族绑定的提示词，族内所有职位的初筛 AI 调用都使用新版本
- 修改族绑定的权重模型，族内所有职位的列表 / 详情评分按新模型重新计算
- 详情页展示的评分按候选人投递职位**所属族**配置的权重模型计算（同一族内候选人评分口径完全一致）
- **权重模型只属于职位族**：职位编辑页不展示任何权重模型相关字段、不提供权重模型管理入口；调整权重模型需到所属族卡片的"配置权重模型"入口
- 详情页支持切换同族内的可用模型做横向对比（可选范围限定为该族自身的模型列表）

### 2. 别名匹配生效

- **匹配方式：纯精准匹配**。职位（主名）和别名都通过精准匹配识别，不使用关键词匹配、不使用包含匹配、不使用模糊匹配
- 邮件主题或文件名**精准匹配**上职位主名时，归位到该职位
- 邮件主题或文件名**精准匹配**上某个职位的别名时，归位到该职位
- 同一职位下同名别名无法重复保存
- 任意两个职位之间（不论是否同族），主名 vs 主名、主名 vs 别名、别名 vs 别名都不能重复

### 3. 历史曾用名兼容

- 历史上使用过、但当前系统中已不存在的职位名称，HR 添加为别名后，历史简历能被识别并归位
- 新简历使用已配置的别名时，能正确归位

### 4. 族管理

- 删除族时族内不能有任何关联简历
- 删除职位时禁止删除有评估结果的职位
- 停用族时需确认，组内没有还在启用的职位
- 启用族时无前置条件，直接启用
- 族的启停与职位的启停独立维护，互不影响

### 5. 兼容性

- 现有职位数据不丢失
- 现有简历的关联关系不丢失
- 现有评估结果不丢失
- 历史数据自动按规则归入族内
