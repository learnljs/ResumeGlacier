# 重构提示词模板库

配合 `.claude/skills/refactor.md` 使用。按场景复制模板，把 `[占位符]` 替换成实际内容。

---

## P0 · 现状盘点（重构前先摸底）

> 对项目做一次重构前的现状盘点，输出一份《重构候选清单》，**不要修改任何代码**：
>
> 1. 找出重复代码（同一逻辑出现在 ≥2 处的）、死代码（无引用）、超长函数（>60 行）、深嵌套（>3 层）
> 2. 找出 `any` 的使用点、被忽略的错误处理（空 catch、吞异常）
> 3. 找出模块耦合点（跨层直接访问数据库、组件直接调 API、服务层职责混杂等）
> 4. 检查是否还有实习/公司特定残留（硬编码组织名、专属集成遗留、内部域名/邮箱、内部文档引用）
>
> 按「风险等级 × 收益」排序输出，每项给出：位置、问题、建议动作（提取 / 合并 / 删除 / 重写）、涉及文件。
>
> 提示：本项目已完成一次盘点，结论见 `docs/refactor-audit.md`，可在此基础上增量更新。

## P1 · 重构计划（每次动手前必用）

> 我要重构 [模块名]，目标是 [提升可维护性 / 修复结构问题 / 提升代码质量]。
> 请先输出重构计划，**不要动手写代码**：
>
> 1. 涉及的文件清单（含将被新建 / 删除 / 移动的文件）
> 2. 改动顺序与每步的验证方式
> 3. 行为是否会有任何变化（API 响应、状态流转、UI、数据库写入）
> 4. 风险点与回滚方案
> 5. 是否触碰兼容红线（SQLite 约束、加密字段、废弃字段、外部契约）
>
> 确认后我再让你执行。

## P2 · 单模块重构（结构优化）

> 重构 [文件/模块]，遵循以下约束：
>
> - 行为完全不变，只调整代码结构（提取函数、合并重复、简化嵌套、理顺分层）
> - 只改这个模块，不碰其他文件
> - 不新增依赖、不做投机性抽象
> - 保持现有命名、导入风格（`@/*` 别名）、错误处理风格
>
> 完成后运行 `npm run lint && npx tsc --noEmit && npm run build` 验证，并报告：改了哪些函数、是否有行为变化。

## P3 · 行为对照审查（重构后必做）

> 审查我这次重构的 diff（`git diff`），重点确认：
>
> 1. 外部行为是否有意外变化：API 响应字段、状态流转、错误信息、UI 文案与展示
> 2. 是否有「顺手优化」混入本次重构范围（应拆出单独处理）
> 3. 是否有死代码 / 无用导入残留
> 4. 是否满足项目约定（kebab-case 服务文件、`cn()` 合并 className、设计令牌、中文注释）
>
> 按「阻塞 / 建议 / 风格」分级输出，只列事实与位置，不泛泛而谈。

## P4 · 代码质量提升（类型与健壮性）

> 提升 [文件/模块] 的代码质量，约束如下：
>
> - 消除 `any`，用精确类型；补齐缺失的返回类型
> - 错误处理：空 catch 必须处理或明确注释原因；保持中文错误信息风格
> - 提取超过 60 行 / 嵌套超过 3 层的逻辑
> - 不改业务行为，不新增依赖
>
> 完成后跑 lint / tsc / build，报告每处改动及其理由。

## P5 · UI 重设计（约束内重设计）

> 基于现有设计令牌（**石墨主题**，定义在 `app/globals.css` 的 `:root`，`tailwind.config.ts` 已注册 sidebar/success/warning/info 色系）重设计 [页面/组件]：
>
> - 颜色只能使用设计令牌（`--primary` / `--accent` / `--destructive` / `--success` / `--warning` / `--info` / `--background` / `--sidebar*` 等），禁止硬编码色值（`bg-yellow-100`、`text-blue-600` 这类）；如确需新色，先加到 `globals.css` 并说明理由
> - 保持 shadcn/ui 组件模式（`components/ui/`），用 `cn()` 合并 className
> - 中文 UI 文案；保持现有页面交互与数据流不变（只动展示层）
> - 移动端响应式与现有导航结构保持一致
> - 完整清单见 `ui重新设计.md`（B12 执行子文档）；视觉参考 `.ui-mockups/`（variant-a 为旧「墨金·朱」方案，现以石墨令牌为准）
>
> 完成后用 Playwright MCP 截图对比，报告改动点与视觉变化。

## P6 · 整体审查（重构收尾）

> 按 `REVIEW.md` 的审查要点审查整个重构成果：
>
> - Spec 一致性、命名规范、架构合规（SQLite 约束、组件分层）
> - 边界与异常路径覆盖（队列崩溃恢复、解析失败、Webhook 推送失败）
> - 确定性逻辑是否都写成显式代码（重试、路由、阈值、硬条件、规则打标）
> - 样式规范（`cn()`、设计令牌）
>
> 输出审查报告，按「阻塞 / 建议」分级。

## P7 · 个人化清理（实习 → 个人项目）

> 把项目从「实习项目」清理为「个人项目」：
>
> 1. 找出并清理公司/实习特定残留：硬编码组织名、专属集成遗留、内部域名/邮箱、内部文档引用
> 2. 检查 `README.md`、`CONTRIBUTING.md`、`package.json`（name/author/repository/private）、LICENSE 署名、运行说明中的相关表述，改为个人项目口吻
> 3. 决定项目新名称后全仓统一替换（含 CLAUDE.md / REVIEW.md）
> 4. 不改变功能行为；每个改动单独列出
>
> 输出改动清单后逐个执行。
